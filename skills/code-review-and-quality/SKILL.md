# 代码评审与质量门禁

目标：任何改动合入主干前都过一遍多轴评审，产出**分级、可执行**的评审意见，而不是一句 LGTM 或一堆平铺的挑刺。

**通过标准**：改动确实让代码整体健康度变好就批准，不要求完美 —— 完美代码不存在，目标是持续改进。不要因为「写法跟我不一样」就卡住；只要变好且符合项目既有约定，就该过。

**铁律**：没有证据的 LGTM 等于没评审；把真问题说成「可能有点小问题」是不诚实；把「这个太复杂」当结论等于把问题丢回给作者。

## 什么时候用

- 合并任何 PR / 改动之前
- 功能实现完成之后
- 评审别的 agent 或模型产出的代码
- 重构现有代码之后
- 修完任何 bug 之后（同时评审修复和回归测试）
- 用户贴了一段 diff 让你看「有没有问题」时（即使很短）

## 五轴评审

每一轴都要给结论，不要只看测试是否通过。

### 1. 正确性（Correctness）

代码是否真的做了它声称要做的事？

- 与 spec / 任务要求一致吗？
- 边界情况处理了吗（null、空集合、边界值、并发）？
- 错误路径处理了吗，不只是 happy path？
- 测试通过吗？测试测的是**行为**还是实现细节？
- 有没有 off-by-one、竞态、状态不一致？

### 2. 可读性与简洁（Readability & Simplicity）

别人（或下一个 agent）不看作者解释能不能读懂？

- 命名是否达意、与项目约定一致（禁止无语境的 `temp`、`data`、`result`）
- 控制流是否直白（避免嵌套三元、深层回调）
- 相关代码是否放在一起，模块边界是否清楚
- 有没有该拆掉的「聪明」技巧
- **能不能用更少的行做到？**（100 行够用却写了 1000 行视为失败）
- **抽象配得上它的复杂度吗？**（第三次出现同类需求前不要泛化）
- 注释解释的是意图，不是复述代码
- 有没有死代码残留：无意义变量（`_unused`）、向后兼容 shim、`// removed` 注释
- **是不是往无关流程上硬加了一个分支？** 这是设计味道，不是小 nit —— 把逻辑放进自己的 helper / 状态 / 策略里，别缠进已有路径
- **同一形状的条件判断是否反复出现？** 那通常意味着缺一个模型或分发器；「临时」分支基本都会变成永久债

### 3. 架构（Architecture）

改动是否贴合系统设计？

- 沿用既有模式还是引入新模式？新模式有理由吗？
- 模块边界是否干净？有没有该共享的重复代码？
- 依赖方向正确吗（无循环依赖）？
- 抽象层级合适吗（既不过度设计，也不过度耦合）？
- **这次重构是降低了复杂度，还是把复杂度搬了个地方？** 数一数读者为了跟上改动必须同时握住几个概念。如果所谓「更干净」的版本没让这个数字变小，它就不更干净 —— 优先选让整段分支 / 模式 / 层级消失的改法，而不是把同样的逻辑重新集中一遍。**删掉一个抽象优于打磨它。**
- **是否把 feature 相关逻辑漏进了共享模块？** 逻辑留在它所属的层；复用既有标准 helper，而不是造一个近似副本；不要默认接受架构漂移。
- **类型边界是否显式？** 质疑无必要的 `any` / `unknown` / optional / 强制转换，以及掩盖不明确不变量的静默兜底 —— 把边界写清楚，往往连带让周围控制流变简单。

### 4. 安全（Security）

改动是否引入漏洞？

- 用户输入是否校验与净化？输出是否编码（防 XSS）？
- 密钥是否排除在代码、日志、版本库之外？
- 需要的地方是否校验了认证 / 授权？
- SQL 是否参数化（禁止字符串拼接）？
- 依赖来源可信、无已知漏洞？
- 外部数据（API、日志、用户内容、配置文件）是否一律按不可信处理，只在系统边界处校验后进入逻辑或渲染？

需要更细的安全条目时，按「危险路径操作、CORS、安全响应头、依赖安装脚本、LLM 输出信任边界」逐项过一遍。

### 5. 性能（Performance）

改动是否引入性能问题？

- 有没有 N+1 查询？
- 有没有无界循环、无上限的数据拉取、列表接口缺分页？
- 有没有该异步却同步的操作？
- UI 组件有没有不必要的重渲染？
- 热路径上有没有创建大对象？

## 结构性改法：给方案，不只给问题

指出结构问题时，**顺手提出具名改法**。只说「这里很复杂」等于让作者猜。可用的改法：

- 用带类型的模型或显式分发器**替掉一长串条件判断**
- 把重复分支**合并成一条更清楚的流程**
- **拆开编排层与业务逻辑**，各自独立可读
- 把 feature 逻辑**移出共享模块**，放到拥有该概念的包
- **复用标准 helper**，别造近似副本
- **把类型边界写显式**，让下游分支消失
- **删掉只增加绕路的透传包装**
- **抽出 helper，或把大文件拆成聚焦的小模块**

优先选「减少零件」的改法，而不是把同样的复杂度摊到更多地方。

## 改动规模

小而聚焦的改动更好评审、更快合入、更安全发布。

```
~100 行   → 好，一口气能评审完
~300 行   → 可以接受，前提是单一逻辑改动
~1000 行  → 太大，拆开
```

**除了 diff 大小，还要看文件大小**：小 diff 也可能把单文件推过健康边界 —— 单文件**总量**接近 1000 行是常见的检视信号（不是硬上限）。改动让一个本就很大的文件继续变大时，先问要不要抽 helper / 子组件 / 模块，**先拆再加**。

**什么算「一个改动」**：单一自洽的修改，解决一件事，带相关测试，提交后系统仍可用。是功能的一部分，不是整个功能。

改动太大时的拆分策略：

| 策略 | 做法 | 适用 |
|---|---|---|
| 堆叠 | 先提小的，基于它再做下一个 | 有先后依赖 |
| 按文件组 | 需要不同评审者的部分分开提 | 横切关注点 |
| 横向 | 先建共享代码 / 桩，再接调用方 | 分层架构 |
| 纵向 | 按功能切成小的全栈切片 | 功能开发 |

**大改动可以接受的情况**：整文件删除、自动化重构 —— 评审者只需确认意图，不必逐行看。

**重构与功能分开提**：既重构又加新行为的改动是两个改动。小幅清理（改变量名）可由评审者酌情带上。

## 改动描述

每份改动都要能在版本历史里独立读懂。

**首行**：短的祈使句，能独立成立。「Delete the FizzBuzz RPC」，不要「Deleting the FizzBuzz RPC」。要让搜索历史的人不看 diff 也能懂。

**正文**：改了什么、为什么。写清代码里看不出来的上下文、决策与取舍，链上 bug 号、benchmark、设计文档。方案有短板就承认。

**反例**：「fix bug」「fix build」「add patch」「move code from A to B」「phase 1」「add convenience functions」。

## 评审流程

### 第 1 步：先理解意图

看代码之前先回答：

```
- 这个改动想达成什么？
- 它实现的是哪份 spec / 任务？
- 预期行为变化是什么？
```

### 第 2 步：先看测试

测试暴露意图和覆盖面：

```
- 针对这个改动有测试吗？
- 测的是行为还是实现细节？
- 边界覆盖了吗？
- 测试名有描述性吗？
- 如果代码变了，这些测试抓得住回归吗？
```

最后一条**用实验回答，不要只靠读**：把改动新增的一个条件取反（去掉一个否定、把 `&&` 换成 `||`），跑测试，再从备份恢复文件。改完还绿的变异测试就是一条发现 —— 明确指出缺哪个用例。

### 第 3 步：看实现

带着五轴逐个文件走：

```
对每个改动文件：
1. 正确性：代码做了测试说它该做的事吗？
2. 可读性：不看解释我能读懂吗？
3. 架构：贴合系统吗？
4. 安全：有漏洞吗？
5. 性能：有瓶颈吗？
```

### 第 4 步：给发现分级

报发现之前，先对照调用方、守卫和测试确认它成立；被它们排除的就丢掉。**既有缺陷与本改动引入的回归要分开标注。**「零发现」是合法结论，不要为了凑数硬编。

每条意见都带级别，让作者知道哪些必须改：

| 前缀 | 含义 | 作者动作 |
|---|---|---|
| （无前缀） | 必须改 | 合并前处理 |
| **Critical:** | 阻塞合并 | 安全漏洞、数据丢失、功能损坏 |
| **Nit:** | 可选 | 可以忽略 —— 格式、风格偏好 |
| **Optional:** / **Consider:** | 建议 | 值得考虑，非必须 |
| **FYI** | 仅告知 | 无需动作，留作背景 |

**先说要紧的**：按杠杆排序 —— 正确性和安全在前，然后是结构性回归和该做的简化，最后才是其它。别让真问题埋在一堆外观 nit 下面；几条高质量意见胜过长清单。如果一个结构问题加十个 nit，**那个结构问题就是这份评审**。

### 第 5 步：检查「验证故事」

```
- 跑了哪些测试？
- 构建过了吗？
- 手工验过吗？
- UI 改动的截图呢？
- 有前后对比吗？
```

## 多视角评审

不同模型有不同盲区，高风险改动值得换个视角再看一轮：

```
模型 A 写代码
    │
    ▼
模型 B 评审正确性与架构
    │
    ▼
模型 A 处理反馈
    │
    ▼
人做最终判断
```

给评审方的提示模板：

```
请评审这次代码改动的正确性、安全性，以及与项目约定的符合度。
spec 要求 [X]，改动应该 [Y]。
发现按 Critical / Required / Optional / Nit 分级。
```

## 死代码清理

任何重构或实现改动之后，检查有没有变成孤儿的代码：

1. 找出已不可达 / 无人引用的代码
2. 逐项列出来
3. **删之前先问**：「这些现在没人用了，可以删吗：[清单]？」

不要留死代码 —— 它会误导后续读者和 agent。但也不要静默删掉自己没把握的东西，拿不准就问。

```
发现死代码：
- src/utils/date.ts 的 formatLegacyDate() —— 已被 formatDate() 取代
- src/components/ 的 OldTaskCard —— 已被 TaskCard 取代
- src/config.ts 的 LEGACY_API_URL —— 已无引用
→ 可以删掉这些吗？
```

## 评审节奏

评审慢会卡住整条链路；切换过去评审的成本，小于让别人干等。

- **一个工作日内响应** —— 这是上限，不是目标
- 请求到达后尽快给第一轮反馈；一个普通改动应当能在一天内走完多轮
- **优先做到快速单轮反馈**，而不是一次就给出最终批准
- 改动太大时，请作者拆开，而不是硬评一大坨

## 分歧处理

按这个优先级裁决：

1. **技术事实与数据** 高于个人意见和偏好
2. **风格指南** 是风格问题的最终依据
3. **软件设计** 按工程原则评估，不按个人口味
4. **与代码库一致** 可接受，前提是不损伤整体健康度

**不要接受「我之后再清理」。** 经验上延迟清理基本不会发生。除非真在救火，否则要求提交前清理干净；本次改动确实覆盖不到的周边问题，要求开一个 bug 并指派给自己。

## 诚实

- **不要橡皮章。** 没有评审证据的 LGTM 对谁都没用。
- **不要软化真问题。** 会上生产的 bug 说成「可能有点小疑虑」就是不诚实。
- **能量化就量化。**「这个 N+1 会让列表每项多 ~50ms」胜过「这可能会慢」。
- **该反对就反对。** 讨好是评审里的一种失败模式；实现有问题就直说并给替代方案。
- **被推翻时优雅接受。** 作者掌握全部上下文时，尊重其判断。评代码，不评人 —— 把针对人的说法改写成针对代码。

## 依赖纪律

加任何依赖之前：

1. 现有技术栈解决不了吗？（通常能）
2. 这个依赖多大？（看 bundle 影响）
3. 还在维护吗？（看最后提交、未关闭 issue）
4. 有已知漏洞吗？（`npm audit`）
5. 许可证兼容吗？

**规则**：优先标准库和现有工具，每个依赖都是负债。

**升级已有依赖**同样是一次代码改动，最危险的升级就是「bump deps」一锅端：

1. **读 changelog，不只看版本号。** semver 是维护者的承诺，可能没守住；patch 也可能带行为变化。大版本升级要读迁移说明，找出会坏什么。
2. **一次一个依赖。** 单独升级单独合入。一锅端断了构建，你不知道是哪个包干的；单包改动让原因和回滚都干净。
3. **让测试拍板。** 升级前后都要绿；覆盖率薄的地方，缺测试本身就是发现 —— 先补测试。
4. **留意传递依赖图。** 装进来的大多数包没人主动选过。看 lockfile 的 diff，不只看 `package.json`；一次直接升级可能引入几十条间接变化。
5. **lockfile 要诚实。** 提交它、评审它的 diff、永不手改 —— 它才是真正钉住发布内容的东西。

## 常见自我合理化

| 说法 | 事实 |
|---|---|
| 「我自己写的，我知道它是对的」 | 作者对自己的假设是盲的。任何改动都值得另一双眼睛。 |
| 「之后会清理」 | 之后不会来。评审就是质量门禁，现在用起来；要求合并前清理。 |
| 「AI 生成的代码应该没问题」 | AI 代码要更严而不是更松 —— 它自信、看似合理，即使错了。 |
| 「测试都过了，所以没问题」 | 测试必要但不充分，抓不到架构问题、安全隐患、可读性问题。 |
| 「重构之后更干净了」 | 搬家不等于降低。读者仍要握同样多的概念，结构就没变好。 |
| 「只是往这个文件里加一点」 | 小 diff 也会把文件推过健康体积、往无关流程上挂分支。看结果结构，不看 diff 大小。 |
| 「只是升个版本」 | 升级是你没写过的行为变化。读 changelog，semver 不保证不破。 |
| 「一次 PR 全升了省时间」 | 一锅端断了构建就找不到元凶。一次一个依赖，原因和回滚都清楚。 |

## 红旗

- 没评审就合并的 PR
- 「评审」只看测试是否通过（其它四轴不看了）
- 没有评审证据的 LGTM
- 安全敏感改动没有安全视角的评审
- 大到「没法好好评审」的 PR（应该拆）
- 修 bug 的 PR 不带回归测试
- 意见不带级别标注（分不清必须改还是可选）
- 接受「我之后修」—— 之后不会来
- 重构只是把代码挪了个位置，没减少读者要握的概念数
- 改动把本就很大的文件继续变大，而不是先拆
- 新的条件判断散落进无关代码路径（缺一层抽象）
- 自造近似 helper、或把 feature 逻辑塞进共享模块
- 一锅端「bump dependencies」的 PR，既没读 changelog 也没隔离
- lockfile 被手改、没提交、或没看 diff 就合入

## 验证

评审结束后：

- [ ] 所有 Critical 已解决
- [ ] 所有必改项已解决，或有明确理由并记录为延后
- [ ] 测试通过
- [ ] 构建成功
- [ ] 验证故事写清楚了（改了什么、怎么验的）
- [ ] 依赖升级读过 changelog、按包隔离、测试前后都绿，且看过 lockfile diff

**应当直接拦下的情形**（除非改动确实让结构更糟，否则先给简化方案再升级为必改）：重构只搬家不降复杂度；把文件推过体积边界却不拆；把 feature 逻辑加进共享模块；自造既有标准 helper 的近似副本；用静默兜底掩盖不明确的不变量。
