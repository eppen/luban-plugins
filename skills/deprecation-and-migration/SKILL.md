# 下线与迁移

## 总览

代码是负债，不是资产。每一行代码都有持续的维护成本 —— 要修 bug、升依赖、打安全补丁、带新人上手。**下线**是删掉那些已经挣不回成本的代码的纪律，**迁移**是把使用方从旧的搬到新的这个过程。

多数工程组织擅长造东西，很少擅长删东西。这个技能就是补这个缺口。

## 什么时候用

- 用新系统 / API / 库替换旧的
- 下线不再需要的功能
- 合并重复实现
- 清理没人负责但人人依赖的死代码
- 规划一个新系统的生命周期（下线计划从设计时就开始）
- 决定是继续维护遗留系统，还是投入做迁移

## 核心原则

### 代码是负债

每一行代码都有持续成本：测试、文档、安全补丁、依赖升级，以及任何在附近工作的人的心智负担。代码的价值在于它提供的功能，不在于代码本身。同样的功能能用更少的代码、更低的复杂度、更好的抽象提供时 —— 旧代码就该走。

### Hyrum 定律让删除变难

用户足够多时，每一个可观察行为都会被依赖 —— 包括 bug、时序上的怪癖、没写进文档的副作用。所以下线需要**主动迁移**，不只是发通告。当使用方依赖了替代品没复制出来的行为时，他们没法「直接切过去」。

### 下线计划从设计时开始

造新东西时先问：「三年后我们要怎么把它删掉？」接口干净、有 feature flag、暴露面小的系统，比到处泄漏实现细节的系统好下线得多。

## 下线决策

下线任何东西之前，先回答：

```
1. 这个系统还在提供独有的价值吗？
   → 在，就维护。不在，往下走。

2. 有多少使用方依赖它？
   → 量化迁移范围。

3. 替代品存在吗？
   → 不存在就先造替代品。没有替代方案就不下线。

4. 每个使用方的迁移成本是多少？
   → 能轻易自动化的就做。手工成本高的，和继续维护的成本比一比。

5. 不下线的持续维护成本是多少？
   → 安全风险、工程师时间、复杂度带来的机会成本。
```

## 强制下线 vs 建议下线

| 类型 | 什么时候用 | 机制 |
|------|-----------|------|
| **建议型** | 迁移可选，旧系统稳定 | 告警、文档、提醒。使用方按自己的节奏迁。 |
| **强制型** | 旧系统有安全问题、阻碍进展，或维护成本不可持续 | 硬截止日。某年某月某日移除。同时**必须**提供迁移工具。 |

**默认走建议型。** 只有维护成本或风险足以支撑「强制」时才用强制型。强制下线必须配迁移工具、文档和支持 —— 你不能只发一个截止日通告。

## 迁移流程

### 第 1 步：先造替代品

没有能用的替代方案就别下线。替代品必须：

- 覆盖旧系统的全部关键用例
- 有文档和迁移指引
- 在生产环境验证过（不是「理论上更好」）

### 第 2 步：通告并写文档

```markdown
## 下线通告：OldService

**状态：** 2025-03-01 起弃用
**替代：** NewService（见下方迁移指引）
**移除时间：** 建议型 —— 暂无硬截止
**原因：** OldService 需要手工扩容，且缺少可观测性。
          NewService 这两件事都是自动的。

### 迁移指引
1. 把 `import { client } from 'old-service'` 换成 `import { client } from 'new-service'`
2. 更新配置（示例见下）
3. 跑迁移校验脚本：`npx migrate-check`
```

### 第 3 步：增量迁移

一次迁一个使用方，不要一把梭。对每个使用方：

```
1. 找出它和旧系统的所有接触点
2. 改成用替代品
3. 验证行为一致（测试、集成核对）
4. 删掉对旧系统的引用
5. 确认没有回归
```

**推土机规则（Churn Rule）：** 基础设施是你负责下线的，你就有责任把使用方迁走 —— 或者提供无需迁移的向后兼容更新。不要发个弃用通告就把问题丢给使用方自己解决。

### 第 4 步：删除旧系统

只在使用方全部迁完之后：

```
1. 确认活跃用量为零（指标、日志、依赖分析）
2. 删代码
3. 删掉相关测试、文档、配置
4. 删掉下线通告
5. 庆祝一下 —— 删代码是成就
```

## 迁移模式

### 绞杀者模式

新旧系统并行跑，把流量逐步从旧切到新。旧系统处理 0% 流量时，删掉它。

```
阶段 1：新系统 0%，旧系统 100%
阶段 2：新系统 10%（金丝雀）
阶段 3：新系统 50%
阶段 4：新系统 100%，旧系统空转
阶段 5：删除旧系统
```

### 适配器模式

写一个适配器，把旧接口的调用翻译到新实现。使用方继续用旧接口，你在后端换实现。

```typescript
// 适配器：旧接口，新实现
class LegacyTaskService implements OldTaskAPI {
  constructor(private newService: NewTaskService) {}

  // 旧的方法签名，委托给新实现
  getTask(id: number): OldTask {
    const task = this.newService.findById(String(id));
    return this.toOldFormat(task);
  }

  // 把新形状翻译回旧使用方期望的样子
  private toOldFormat(task: Task): OldTask {
    return { id: Number(task.id), title: task.title, done: task.status === 'done' };
  }
}
```

### feature flag 迁移

用开关把使用方一个一个从旧系统切到新系统：

```typescript
function getTaskService(userId: string): TaskService {
  if (featureFlags.isEnabled('new-task-service', { userId })) {
    return new NewTaskService();
  }
  return new OldTaskService();
}
```

### 数据库 schema 迁移（expand / contract）

schema 改动是风险最高的一类迁移，因为数据是唯一「回滚部署也回不去」的东西。典型的失败模式是把 schema 改动和代码改动绑在同一次发布里：在开始用新列名的同一版里重命名列，而在滚动发布窗口内新旧代码同时在跑 —— 其中一方查的列根本不存在。解法是**永远不要原地改列**，按可加的阶段推进，让每一步新旧代码都合法。

```
EXPAND ──────────────→ MIGRATE ──────────────→ CONTRACT
加新列（可空），        回填历史数据，           确认没有代码再读
与旧列并存             应用双写新旧两列         旧列后，另起一次部署删除
```

**完整示例 —— 把 `name` 改名为 `full_name`：**

1. **Expand。** 加可空的 `full_name`。部署。（旧代码忽略它，不会坏。）
2. **双写。** 应用每次插入 / 更新同时写 `name` 和 `full_name`。部署。
3. **回填。** 分批把历史行的 `name` 拷到 `full_name`，避免锁表。
4. **切读。** 应用改为读 `full_name`，仍然双写。部署并观察一段时间。
5. **Contract。** 停止写 `name`，然后在**另一次、更晚的**部署里删掉这一列。

每一步都能独立部署、独立回退：第 4 步出问题，把代码回滚，`full_name` 依然在被写入。把每个阶段当成一条薄的纵向切片 —— 见 `incremental-implementation`。

**规则：**
- **先加后删，破坏性操作单独发。** 加（新可空列、新表、新索引）在任何部署里都安全；删和改名要**在没有代码引用旧形状之后**单独发一次。
- **每个迁移都要有测过的回滚路径。** 回不去的迁移就是回不去的部署。合并之前写好并跑一遍 `down`。
- **回填要分批、避开热路径。** 一条 `UPDATE` 扫几百万行会锁表；分块并限速。
- **建大索引不要阻塞写入**（如 Postgres 的 `CREATE INDEX CONCURRENTLY`）。
- **切换风险高时用 feature flag 与代码解耦**，与上面的 feature flag 迁移模式完全一致。

## 僵尸代码

僵尸代码是没人负责但人人依赖的代码。它没在被积极维护，没有明确的负责人，持续累积安全漏洞和兼容性问题。迹象：

- 6 个多月没有提交，但仍有活跃使用方
- 没有指定的维护者或团队
- 有失败的测试但没人修
- 依赖有已知漏洞但没人升级
- 文档里引用的系统早就不存在了

**应对：** 要么指定负责人认真维护，要么配一份具体迁移计划下线它。僵尸代码不能一直挂在灰区 —— 要么投入，要么移除。

## 常见自我合理化

| 合理化 | 现实 |
|---|---|
| 「它还能跑，为什么要删」 | 没人维护但能跑的代码在累积安全债和复杂度。维护成本是悄悄涨的。 |
| 「以后可能会有人用」 | 真要用的时候可以重建。把没用的代码「以防万一」留着，成本比重建更高。 |
| 「迁移太贵了」 | 把迁移成本和未来 2-3 年的持续维护成本比一比。长期看迁移通常更便宜。 |
| 「等新系统做完再下线旧的」 | 下线计划从设计时开始。等新系统做完，你已经有新的优先级了。现在就规划。 |
| 「使用方会自己迁」 | 不会。要么提供工具、文档和激励，要么你自己迁（推土机规则）。 |
| 「两套系统可以无限期共存」 | 两套做同一件事的系统，意味着双倍的维护、测试、文档和上手成本。 |
| 「改个列名而已，就一行」 | 滚动发布期间新旧代码同时在跑 —— 总有一方查的列已经不存在了。expand/contract，绝不原地改名。 |
| 「加列和删旧列放同一个迁移里」 | 那等于把一次安全的「加」和一次破坏性的「删」绑死。删除要单独一次部署，且在没有代码引用旧形状之后。 |
| 「需要回滚的时候再写」 | 没有 down 路径的迁移就是回不去的部署。合并之前写好并跑一遍 `down`。 |

## 红旗

- 要下线的系统却没有可用替代品
- 只有下线通告，没有迁移工具和文档
- 「软」下线挂了好几年、一直只是建议、毫无进展
- 僵尸代码：没有负责人，却有活跃使用方
- 还在给已下线的系统加新功能（该投到替代品上）
- 没测当前用量就下线
- 没确认活跃使用方为零就删代码
- schema 改动和依赖它的代码在同一次部署里发出去
- 原地重命名或删除列，而不是走 expand/contract
- 合并了没有测过 down 路径的迁移，或者回填会锁表

## 验证

一次下线做完之后：

- [ ] 替代品已在生产验证，覆盖全部关键用例
- [ ] 有迁移指引，含具体步骤和示例
- [ ] 所有活跃使用方都已迁移（用指标 / 日志核实）
- [ ] 旧代码、测试、文档、配置全部移除
- [ ] 代码库里不再有任何对已下线系统的引用
- [ ] 下线通告已删掉（它们已经完成使命）

一次数据库 schema 迁移之后：

- [ ] 改动按可加阶段发布（expand → 回填 → contract），不是一次原地修改
- [ ] 每一个部署步骤上，新旧代码对 schema 都是合法的
- [ ] 每个迁移都有测过的 down 路径；回填是限速分批跑的
- [ ] 破坏性步骤（删 / 改名）在「没有代码引用旧形状」之后单独部署
