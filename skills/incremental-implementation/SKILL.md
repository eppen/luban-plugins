# 增量实现

## 总览

按薄的纵向切片来建 —— 实现一块、测它、验它、然后扩展。不要一遍把整个功能写完。每一次增量结束时，系统都应该处于可工作、可测试的状态。正是这条执行纪律，让大功能变得可控。

## 什么时候用

- 实现任何跨文件的改动
- 按任务拆解建新功能
- 重构既有代码
- 任何你「想在跑测试之前先写超过约 100 行」的时刻

**什么时候不用**：单文件、单函数、范围本来就极小的改动。

## 增量循环

```
┌──────────────────────────────────────┐
│                                      │
│   实现 ──→ 测试 ──→ 验证 ──┐         │
│       ▲                    │         │
│       └───── 提交 ◄────────┘         │
│              │                       │
│              ▼                       │
│          下一片                      │
│                                      │
└──────────────────────────────────────┘
```

对每一片：

1. **实现**最小的一块完整功能
2. **测试** —— 跑测试套件（没有测试就先写一个）
3. **验证** —— 确认这一片按预期工作（测试通过、构建成功、人工核对）
4. **提交** —— 用描述性的信息保存进度（原子提交的做法见 `git-workflow-and-versioning`）
5. **进入下一片** —— 往前推，不要推倒重来

## 切片策略

### 纵向切片（首选）

打穿一整条完整路径：

```
切片 1：新建任务（DB + API + 基础 UI）
    → 测试通过，用户能在界面上建一条任务

切片 2：任务列表（查询 + API + UI）
    → 测试通过，用户能看见自己的任务

切片 3：编辑任务（更新 + API + UI）
    → 测试通过，用户能改任务

切片 4：删除任务（删除 + API + UI + 二次确认）
    → 测试通过，CRUD 完整
```

每一片都交付能跑通的端到端功能。

### 契约先行切片

前后端需要并行开发时：

```
切片 0：定下 API 契约（类型、接口、OpenAPI 描述）
切片 1a：按契约实现后端 + API 测试
切片 1b：按契约用 mock 数据实现前端
切片 2：集成并端到端测试
```

### 风险优先切片

先啃最危险、最不确定的那块：

```
切片 1：验证 WebSocket 连接能建立（风险最高）
切片 2：在已验通的连接上做实时任务更新
切片 3：加离线支持与重连
```

如果切片 1 失败，你是在切片 2、3 投入之前就发现了。

## 实现规则

### 规则 0：简单优先

写代码之前先问：「能工作的最简方案是什么？」

写完之后再对着这几条过一遍：
- 能用更少的行数做到吗？
- 这些抽象挣到了它们带来的复杂度吗？
- 一个资深工程师看到会不会说「你为什么不直接……」？
- 我是在为假想的未来需求写，还是在为当前任务写？

```
简单性检查：
✗ 为一个通知需求做带中间件管道的通用 EventBus
✓ 一个简单的函数调用

✗ 为两个相似组件套抽象工厂
✓ 两个直白的组件 + 共享工具函数

✗ 为三个表单做配置驱动的表单生成器
✓ 三个表单组件

```

三段相似的代码，好过一个过早的抽象。先写朴素但明显正确的版本。等正确性被测试证明了，再谈优化。

### 规则 0.5：范围纪律

只碰任务需要的东西。

不要：
- 「顺手清理」改动旁边的代码
- 重构你没在改的那些文件的 import
- 删掉你没有完全看懂的注释
- 因为「看着有用」就加规格里没有的功能
- 在只是「读一下」的文件里顺手把语法现代化

发现任务范围之外值得改的地方，记下来 —— 但不要改：

```
发现了但不动：
- src/utils/format.ts 有个没用到的 import（和本任务无关）
- 鉴权中间件的报错信息可以更清楚（另开任务）
→ 要我给这两条建任务吗？
```

### 规则 1：一次一件事

每次增量只改一个逻辑上的东西。不要混关注点：

**坏：** 一个提交里同时新增组件、重构旧组件、改构建配置。

**好：** 三个独立提交，一个改一件事。

### 规则 2：保持可编译

每次增量之后，项目必须能构建、既有测试必须通过。不要在切片之间把代码库留在坏掉的状态。

### 规则 3：未完成功能放在 feature flag 后面

功能还没准备好给用户看，但你需要合并增量时：

```typescript
// 进行中的工作放在开关后面
const ENABLE_TASK_SHARING = process.env.FEATURE_TASK_SHARING === 'true';

if (ENABLE_TASK_SHARING) {
  // 新的分享 UI
}
```

这样你可以把小增量合进主分支，又不暴露未完成的东西。

### 规则 4：安全默认值

新代码默认应该是安全、保守的行为：

```typescript
// 安全：默认关闭，显式开启
export function createTask(data: TaskInput, options?: { notify?: boolean }) {
  const shouldNotify = options?.notify ?? false;
  // ...
}
```

### 规则 5：可回滚

每次增量都应该能独立回退：

- 只增不改的改动（新文件、新函数）最好回退
- 对既有代码的修改应该最小、聚焦
- 数据库迁移要配对应的回滚迁移
- 不要在同一提交里先删一样再换成另一样 —— 拆开

## 指挥 agent 做增量

要 agent 增量实现时，把话说明白：

```
我们来实现计划里的任务 3。

先只改数据库 schema 和 API 端点。
先别碰 UI —— 那是下一片的事。

实现完跑一下本仓的测试和构建命令，确认没弄坏东西。
```

每一片都要明确说清什么在范围内、什么不在。

## 增量检查清单

每次增量之后，用本仓自己的命令核对（先摸清本仓怎么测，见 `test-driven-development` 里「先摸清本仓怎么测」）：

- [ ] 这个改动只做一件事，并且做完整了
- [ ] 既有测试全部通过（本仓的测试命令：`npm test`、`./gradlew test`、`pytest`……）
- [ ] 构建成功（本仓的构建命令）
- [ ] 类型检查通过（这套技术栈有的话：`npx tsc --noEmit`、`mypy`……）
- [ ] Lint 通过（本仓的 lint 命令）
- [ ] 新功能按预期工作
- [ ] 改动已用描述性信息提交

**注意：** 只有可能影响结果的改动之后才需要重跑对应命令。跑绿之后，除非代码又变了，不要再重跑同一条命令 —— 在没变的代码上重跑不增加任何信息。

## 常见自我合理化

| 合理化 | 现实 |
|---|---|
| 「最后一起测」 | bug 会叠加。切片 1 里的 bug 会让切片 2-5 全都错。每片都测。 |
| 「一次做完更快」 | 它**感觉**更快，直到某处崩了，而你找不出是 500 行改动里哪一行导致的。 |
| 「这些改动太小了，不值得单独提交」 | 小提交是免费的。大提交藏 bug，还让回滚很痛苦。 |
| 「feature flag 回头再加」 | 功能没完成就不该被用户看见。现在就加。 |
| 「这个重构很小，顺手带上」 | 重构和功能混在一起，评审和排查都更难。分开。 |
| 「再跑一遍构建命令确认一下」 | 跑绿之后重跑同一条命令什么也不增加，除非代码又变了。要跑就在后续改动之后跑，不是用来安心。 |

## 红旗

- 没跑测试就先写了超过 100 行代码
- 一次增量里混了多个不相关的改动
- 「顺便把这个也加上」式的范围扩张
- 为了快而跳过测试 / 验证步骤
- 增量之间构建或测试是坏的
- 大量未提交的改动越积越多
- 第三个用例还没出现就先造抽象
- 「既然来了」就顺手改任务范围外的文件
- 为一次性操作新建工具文件
- 中间没有任何代码变动却连着跑两遍同一条构建 / 测试命令

## 验证

一个任务的所有增量做完之后：

- [ ] 每个增量都单独测过、单独提交过
- [ ] 全量测试通过
- [ ] 构建干净
- [ ] 功能按规格端到端可用
- [ ] 没有遗留未提交的改动
