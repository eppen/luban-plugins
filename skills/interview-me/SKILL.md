# 访谈式需求澄清

## 总览

用户嘴上要的东西，和他实际想要的东西，通常不是一回事。他说「要个 dashboard」，因为别人要 dashboard 时都这么说，不是因为 dashboard 能解决他的问题。他说「弄快一点」，但心里没有数字。

发现这个落差最便宜的时刻，是任何计划、规格、代码都还不存在的时候。一旦开工，切换成本就是真的了，用户会把错的方案合理化成「够用了」，错配就此固化。

这个技能就是在落差还不花钱的时候把它补上。其他 Define 阶段的技能都假定你已经大致知道要什么：`idea-refine` 从一个想法发散出若干变体，`spec-driven-development` 把需求写下来，`doubt-driven-development` 在你起草之后拷问方案。interview-me 是这三者之前的那一步 —— 一次问一个问题，每题都附上你的猜测，直到你能在用户开口前预测他要说什么。

## 什么时候用

- 请求里至少缺一项：**谁**在用、**为什么**要、**成功**长什么样、真正的**硬约束**是什么
- 请求是「惯例式」而非具体的（「给我做个 X」「优化一下」），不靠猜无法展开
- 你正准备拿没摆到台面上的假设开工
- 两个合理的价值取向在打架（简单 vs 灵活、成本 vs 速度），用户没说选哪个
- 用户显式要求：「先访谈我」「拷问我」「开工前确认下我们真的想清楚了」「压力测试一下我的想法」

**什么时候不用**：

- 请求无歧义且自洽（「把这个变量改名」「修这个错别字」）
- 用户明确要求「别问了，先跑起来」
- 纯信息查询（「X 是怎么工作的」「这段代码干什么」）
- 机械操作（改名、格式化、移动文件）
- 你已经有 ≥95% 把握 —— 先读下面的「何时停止」再判断

## 前提：需要一个能回话的用户

这个技能依赖活的、会回应的用户。**不要在非交互场景里跑**：CI、定时任务、自动循环、无人值守的长跑任务。这类场景下遇到欠规格，正确做法是把它作为阻塞项报给用户，而不是自己猜着往下走。

Luban 里提问用 `ask_question`：一次一题，选项 2~6 个，把「我的猜测」写进题干，把「我更倾向的那个」标 `recommended`。不要在一条消息里堆三个问题。

## 流程

### 第 1 步：先说出假设，附一个把握度数字

开问之前，先用**一句话**写下你对用户意图的判断，再加一个诚实的把握度（0–100%）：

```
假设：你想在站着开会时能回答「我们进展怎么样」，而「dashboard」只是顺手想到的载体。
把握度：~30% —— 缺：给谁看、这里的「指标」具体指什么、成功长什么样
```

这个数字是逼自己诚实用的。如果你写了个高数字，却预测不了用户对你接下来三个问题的反应，那这个数字就是错的。按你能站得住的水平写。

把握度低于 ~70% 时，同一行补一句原因（还有什么没解决、缺什么）。用户才知道这场访谈该挖什么，数字也不至于变成一个含糊的信号。

### 第 2 步：一次一个问题，每题附带猜测

格式：

```
问：<一个聚焦的问题>
猜：<你猜他会怎么答，以及你为什么会这么猜>
```

问完等用户反应，再问下一个。

**为什么一次一个，而不是列成一串**：

- 你的一堆假设混在清单里，用户没法逐条反应
- 一次列一串会鼓励扫读，只能拿到表面答案
- 第三个问题往往取决于第一个的答案；一口气全问完，等于把错误的框架锁死
- 用户认真思考的耐心是有限的，一题一题花

**为什么要附带猜测**：

- 用户「改」一个错猜，比从零「生成」一个答案快得多
- 让你把假设押在明处，可以被当场证明是错的，这让你保持诚实
- 这正好把**你的**前提摆了出来 —— 访谈本来就是为了暴露它

这里的风险是用户客气，顺着你的猜测点头。对策：明确表现出「我很乐意被纠错」，并偶尔往你不希望的方向猜，看用户会不会纠正。

### 第 3 步：听出「想要」和「觉得应该要」

最危险的答案，是用户在说「一个深思熟虑的人会怎么答」，而不是他真正想要的。留意：

- 像在复述最佳实践的回答（「我要可扩展的」「要干净架构」）却没有具体所指
- 把决定推给惯例（「大部分 App 都这么做」「标准做法吧」）
- 这类句式：「我应该……」「我猜按规范来说……」「工程上的好做法是……」
- 把 buzzword 当目标 —— 答案是「现代化」「可扩展」「健壮」而不是某个具体结果

听到这些时，问这一句：

> *「如果不用向任何人解释，你实际想要的是什么？」*

这一句常常比前面五句都管用。

### 第 4 步：用用户自己的话复述意图

把握度够高时，把你现在理解的意图写回去。控制在 5–8 行，尽量用他的词，结构化到能逐行确认或纠正：

```
我现在理解的你要的是：

- 结果：    <一行>
- 使用者：  <一行 —— 谁受益>
- 为什么现在：<一行 —— 什么变了>
- 成功标准：<一行 —— 怎么算成功>
- 硬约束：  <一行 —— 真正的限制>
- 不做：    <一行 —— 明确不做什么>

对 / 不对 / 需要改哪行？
```

「不做」这行不能省。分歧有一半来自对「不做什么」的沉默不一致。

### 第 5 步：确认 —— 要明确的「对」，不是「你看着办」

门禁是一个明确的「对」。下面这些都**不算**「对」：

- 「你看着办就行。」→ 用户在委派，说明他也没有 95% 把握。改成两个具体选项让他二选一，重问。
- 「听着不错。」→ 含糊。追问一句「有哪行想改吗？」沉默不是确认。
- 「行，开始吧。」→ 往往是客气地结束对话，不是认可。同样追问。
- 沉默之后来一句「那就开始吧」→ 用户是放弃这场访谈了，不是收敛了。停下来问是不是漏了什么。

如果他纠正了你，把纠正并进去，再复述一遍。直到拿到明确的「对」。

### 第 6 步：终止回合与停手规则（关键）

用户明确确认意图陈述之后：

1. **交付确认过的意图陈述。**
2. **给出下游路径**（存到 `docs/intent/[主题].md`；用 `spec-driven-development` 起草规格；或者规格之后再进任务拆解）。
3. **立刻结束这一回合。** 不要在这一回合里调工具、不要顺手开始下游工作。把控制权交回用户，让他选下一步。

### 何时停止：95% 把握的判据

能对下面这句答「是」，就结束：

> *我能预测用户对我接下来要问的三个问题的反应吗？*

能 → 你们的理解已经对齐，停止访谈，产出复述。不能 → 还没完，继续问下一个问题。

这是个可检验的判据，不是感觉。它同时有个下限：如果你已经问了好几轮还是预测不了，那是关于这个需求本身的信息，不是继续磨下去的理由。停下来说：「我已经问了 X 个问题，仍然预测不了你的反应，说明有个根本性的东西没对上。要不要退一步重新看？」

## 产出

这个技能的产出是一份**被确认过的意图陈述**：第 4 步的复述 + 第 5 步的明确「对」。这就是交付物。规格、计划、任务清单都是下游，它们消费的是这里产出的意图。

如果用户希望意图能留存（跨会话的项目、要交给别人），可以提议存到 `docs/intent/[主题].md`。**只在用户确认后再写。**

## 示例

一个短的「前后对照」。

**没有 interview-me：**

```
用户：帮我做个 dashboard 看我们的指标
Agent：<开始推荐图表库和布局>
```

Agent 一口气假设了：给谁看、什么指标、「我们的」指谁、成功长什么样。这些一条都没被说出来。每一个假设，都是用户将来会说「我不是这个意思」的地方。

**有 interview-me：**

```
用户：帮我做个 dashboard 看我们的指标

Agent：
假设：你想在站着开会时能回答「我们进展怎么样」，而「dashboard」只是顺手想到的载体。
把握度：~30% —— 缺：给谁看、指标具体指什么、成功长什么样

问：说到「我们进展怎么样」，问的人是谁 —— 只有你自己、站会上的工程团队，还是往上一层（你的主管、高管、董事会）？
猜：站会上的工程团队。因为「我们」通常指这个范围，站会也正是问这句话的场合。如果往上给高管看，指标和表述方式都要大改。

用户：其实是我自己。我总是搞不清现在有哪些实验在跑、早期信号是什么样。

Agent：
修正后的理解：不是团队 dashboard，是个人的实验跟踪器。把握度：~60% —— 还缺：「早期信号」指什么、什么状态算完。
问：你缺的是「不知道有哪些实验存在」，还是「看不到它们的结果在同一个地方」？
猜：后者。你手上有一份实验清单，但结果散在五个工具里，手工对账才是你烦的。

用户：其实是前者。我压根没有清单，实验散落在不同文档里。

Agent：<继续>
```

两个问题之后，Agent 发现真实需求根本不是「dashboard」，而是「一份清单」。产物不同、范围不同、工作量也不同。真按 dashboard 做，方向就错了。

## 与其他技能的关系

- **`spec-driven-development`**：下游。确认的意图如果已经足够具体（给谁、要什么、成功标准），交给它写成规格。
- **`planning-and-task-breakdown`**：下游两跳（在规格之后）才算。
- **`source-driven-development`**：正交。interview-me 澄清用户要什么，后者校验框架事实，两者不冲突。

## 常见自我合理化

| 合理化 | 现实 |
|---|---|
| 「需求已经够清楚了」 | 如果此刻写不出一句「用户想要的结果」，就是不够清楚。先跑第 1 步再判断。 |
| 「先做出来给他看更快」 | 做出来再改，成本在返工，而且用户会把错的方案合理化成「也行」。 |
| 「他说了『你看着办』，那我就自己定」 | 「你看着办」是委派，不是决定。改成两个具体选项让他挑，重问。 |
| 「应该多给他几个选项选」 | 选项适用于「用户知道自己要什么、只是在权衡」。他现在还不知道要什么。列选项会扩大搜索面，提问才能收敛。 |
| 「我附上猜测就是在引导他」 | 引导就是目的。改比从零生成快。真正的风险是顺从，不是引导 —— 靠「愿意被证明是错的」来对冲。 |
| 「聊得够多了，我懂了」 | 检验一下：你能预测他对下三个问题的反应吗？不能就是还没懂。 |
| 「他说了『好』，结束了」 | 如果这个「好」跟在含糊的复述后面、或者只是「听着不错」，那是个空心的「好」。具体复述一遍再确认。 |

## 红旗

- 一条消息里问了三个或更多问题：那是问卷，不是访谈
- 提的问题不带自己的猜测：那是在做调查，不是在押注
- 把「你看着办」当成最终答复
- 用户还没明确确认复述，就已经产出规格、计划或任务清单
- 意图一确认就立刻调工具、开始下游工作，而不是先结束回合
- 问题问成「最佳实践是什么」而不是「你实际想要什么」
- 用户给出「显得专业」的回答（可扩展、干净、现代），你没追问它是不是他真正想要的
- 连着三轮把握度没有明显上升：说明你问错了，退一步重新框定
- 把握度低于 ~70% 却不写原因：用户不知道缺什么，就没法帮你补
- 用户确认之前就把意图文档存下去（文档本身暗示了一个他并未给出的「对」）
- 复述里省掉「不做」那行（对非目标的沉默不一致，是错配的一半）

## 验证

- [ ] 第一回合就给出了明确的假设 + 把握度数字
- [ ] 每个低于 ~70% 的数字都配了一行原因（还缺什么）
- [ ] 问题一次一个，每题都附了 agent 自己的猜测
- [ ] 用户给出「显得专业／符合惯例」的回答时，至少问过一次「如果不用向任何人解释，你实际想要什么」
- [ ] 写出了具体复述（结果 / 使用者 / 为什么现在 / 成功 / 约束 / 不做）
- [ ] 用户给的是明确的「对」，不是「你看着办」「听着不错」或沉默
- [ ] 停止点上，agent 能预测它接下来三个问题会得到的反应
- [ ] 拿到明确确认后立刻结束回合，没有调工具、没有开始下游工作
- [ ] 交给下游技能时，用的是确认过的意图，而不是最初那个欠规格的请求
