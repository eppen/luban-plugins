# 可观测性与埋点

## 总览

观测不到的代码，运维不了。可观测性是指：靠代码发出的遥测数据，从外部回答「系统正在做什么、为什么」。埋点不是上线后的补充，而是和测试一样，跟着功能一起写。功能不带遥测上线，第一个用户报的 bug 就会变成考古现场，而不是一次查询。

## 什么时候用

- 在做任何将在生产运行的功能
- 新增服务、端点、后台任务或外部集成
- 一次线上事故排查耗时过长（「我们看不出来发生了什么」）
- 搭或评审告警规则
- 评审一个加入了 I/O、重试、队列或跨服务调用的 PR

**不用于：**
- 诊断此刻正在发生的故障 —— 用 `debugging-and-error-recovery`（可观测性正是让那个技能下次变快的东西）
- 剖析并优化已经量出来的慢 —— 用 `performance-optimization`
- 上线当天的监控清单与回滚触发条件 —— 见 `shipping-and-launch`；本技能负责喂给它的埋点

## 流程

### 1. 埋点之前先定义「正常工作是什么」

没有问题指向的遥测就是噪音。加任何埋点之前，先写下值班工程师会问这个功能的 2–4 个问题：

```
功能：结账支付重试
值班会问的问题：
1. 首次尝试就成功的支付占比多少，重试后成功的多少？
2. 支付彻底失败时，为什么？（服务商报错？超时？校验失败？）
3. 支付服务商是不是比平时慢？
→ 下面每一个信号都必须能帮上其中至少一个问题。
```

说不出问题，就说明还没到能埋点的时候 —— 你会把一切都记下来，然后什么也没学到。

### 2. 每个问题配对的信号

| 信号 | 回答什么 | 成本特征 | 例子 |
|------|---------|---------|------|
| **结构化日志** | 「这一例到底发生了什么？」 | 按事件计；随流量增长 | `payment_failed` + 服务商错误码 |
| **指标** | 「聚合来看多频繁 / 多快？」 | 每个序列固定；查询便宜 | 服务商调用的 p99 延迟 |
| **链路** | 「跨服务时间花在哪了？」 | 按请求计；通常采样 | 一次慢结账，按跳拆开 |

经验法则：指标告诉你**有没有**问题，链路告诉你问题在**哪**，日志告诉你**为什么**。

### 3. 结构化日志

记事件，不记散文。每行日志是一个 JSON 对象，带稳定的事件名和机器可读的字段：

```typescript
// 坏：字符串拼接 —— 查不了，格式还不一致
logger.info(`支付 ${id} 对用户 ${userId} 在 ${n} 次重试后失败`);

// 好：稳定事件名 + 结构化字段
logger.warn({
  event: 'payment_failed',
  paymentId: id,
  provider: 'stripe',
  errorCode: err.code,
  attempt: n,
}, '支付失败');
```

**日志级别 —— 一致地用：**

| 级别 | 含义 | 值班动作 |
|------|------|---------|
| `error` | 不变量被破坏，可能有人需要动手 | 去查 |
| `warn` | 降级但已处理（重试成功、用了兜底） | 看趋势 |
| `info` | 重要的业务事件（下单、任务完成） | 不用管 |
| `debug` | 诊断细节 | 生产默认关 |

**关联 ID 是强制的。** 在系统边界生成（或接收）一个请求 ID，并把它挂到每行日志、每个 span、每次对外调用上。没有它，你没法从交错的日志里还原出单个请求：

```typescript
// Express：每请求一个子 logger，ID 往下游传
app.use((req, res, next) => {
  req.id = req.headers['x-request-id'] ?? crypto.randomUUID();
  req.log = logger.child({ requestId: req.id });
  res.setHeader('x-request-id', req.id);
  next();
});
```

**多个入口写进同一份日志时，把入口点也标上。** 关联 ID 标识「同一次运行」，但不说「是哪条代码路径发起的」。同一个任务，从调度器触发、从重放端点触发、从手工 CLI 触发，写进同一个 sink 的行长得一模一样，于是要归因就只能靠排除法 —— 去翻调度器历史、进程表、部署日志 —— 而这种推理只在那些外部记录恰好还在时才成立。**在运行开始的地方**盖上入口点，并和关联 ID 用同样的方式往下传：

```typescript
// 所有入口共用一个 helper：这次运行的 logger 同时带两个字段。
// 用 entryPoint 而不是 source —— ECS 把 source.* 留给网络字段。
export const runLog = (entryPoint: 'scheduler' | 'replay_endpoint' | 'cli', runId: string) =>
  logger.child({ entryPoint, requestId: runId });

// 调度器 tick        -> runLog('scheduler', crypto.randomUUID())
// POST /jobs/:id/replay -> runLog('replay_endpoint', req.id)
// CLI 调用           -> runLog('cli', process.env.RUN_ID ?? crypto.randomUUID())
```

这两个字段要和关联 ID 一样跨过同样的边界 —— 队列元数据、HTTP 头 —— 否则 worker 会自己重新推导入口点，只能靠猜。仅仅和入口点相关但不等价的字段只是线索，不是归因：任何能触发这个任务的东西都能把它复现出来。

**绝不记录密钥、token、密码或完整 PII。** 这是 `security-and-hardening` 里的硬规则 —— 遥测管道是典型的数据泄露路径。字段走白名单；不要整包记录请求体。

### 4. 指标

请求驱动的服务，在每个端点和每个外部依赖上埋 **RED**：**R**ate（每秒请求数）、**E**rrors（失败率）、**D**uration（延迟直方图，不是平均值）。资源类（队列、连接池、主机）用 **USE**：**U**tilization（利用率）、**S**aturation（饱和度）、**E**rrors。

和链路一样，供应商中立的路线是 OpenTelemetry 的 metrics API（与第 5 步同一套 SDK 和上下文）。下面的例子用 Prometheus 的 `prom-client` —— 只是一种常见的后端选择，不是唯一；RED / USE 和基数规则两种后端完全一样。

```typescript
import { Histogram } from 'prom-client';

const httpDuration = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP 请求耗时',
  labelNames: ['method', 'route', 'status_class'],  // '2xx'，不是 '200'
  buckets: [0.05, 0.1, 0.25, 0.5, 1, 2.5, 5],
});
```

**基数是那个失败模式。** 每一个唯一的 label 组合就是一条独立时间序列。label 必须来自小而固定的集合（路由模板、状态码分类、服务商名）。绝不用用户 ID、原始 URL、错误信息文本等无界值当 label —— 那些属于日志和链路。

```
可以当 label：  route="/api/tasks/:id"   status_class="5xx"   provider="stripe"
绝不当 label：  user_id、email、request_id、完整 URL、错误信息文本
```

**平均值永远不追，百分位永远要看：** 平均值会把那 1% 体验极差的用户藏起来。用直方图，读 p50 / p95 / p99。

### 5. 分布式链路

用 OpenTelemetry —— 供应商中立的标准，自动埋点几乎零代码覆盖 HTTP、gRPC 和常见数据库客户端：

```typescript
// tracing.ts —— 必须在其他任何 import 之前加载
import { NodeSDK } from '@opentelemetry/sdk-node';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';

const sdk = new NodeSDK({
  serviceName: 'checkout-service',
  instrumentations: [getNodeAutoInstrumentations()],
});
sdk.start();
```

手工 span 只加在有意义的内部工作单元上（如 `applyDiscounts`、`chargeProvider`），并附上值班会用来筛选的属性。上下文要跨过每个异步边界传播 —— HTTP 头、队列消息元数据 —— 否则链路在那里就断了。默认按低比例做头部采样；后端支持尾部采样的话，错误全留。

### 6. 告警

对**用户能感觉到的症状**告警，不对原因告警：

```
症状（值得叫人）：                 原因（看板，不叫人）：
错误率 > 1% 持续 5 分钟             CPU 85%
p99 延迟 > 2s                       某个 pod 重启了
队列积压时长 > 10 分钟              磁盘 70%
```

按原因告警，会在没事时乱叫，又会漏掉你没预料到的故障。按症状告警，恰好在用户受损时触发，不管原因是什么。

每条告警都要满足：

1. **必须可行动。** 如果响应是「忽略，它自己会好」，就删掉这条告警。
2. **必须链到 runbook** —— 哪怕三行：它意味着什么、先跑哪条查询、找谁升级。
3. **阈值和持续时间**由 SLO 或历史数据支撑，不是拍脑袋。
4. 只用两个等级：**page**（影响用户，立刻处理）和 **ticket**（降级，本周处理）。第三档会变成噪音，训练人忽略一切。

#### 写 runbook

上面第 2 条要求每条告警链到 runbook。runbook 的任务是让读者不用思考就能回答三件事：正在发生什么、先查什么、查不出来找谁。放在 `docs/runbooks/`，按告警命名。

**最小可用 runbook（三行）：**

```markdown
# Runbook：/api/tasks 错误率高
**意味着：** 数据库连接池可能耗尽，或刚发了坏部署。
**先查：** `SELECT count(*) FROM pg_stat_activity WHERE backend_type = 'client backend';`
  —— 如果数量超过池上限，见第 2 步。（换成你所用数据库的等价查询。）
**升级给：** #db-oncall 或工程值班轮值。
```

**什么时候写得比三行多：** 只有当「先查」那一步不足以判断时，才加步骤。一份覆盖三种最常见原因的五步 runbook，胜过一份覆盖所有边角、只会被人略读的二十步文档。

**runbook 要保持最新。** 每次用它处理完事故，就把对应的更新作为结案的一部分 —— 过期的 runbook 会制造虚假信心。如果某一步是错的或缺失的，改完再标记事故已解决。

### 7. 验证遥测本身

埋点也是代码，也会错。宣布干完之前，主动触发那些路径，看真实输出：

- 在预发环境造一个错误 → 用 `requestId` 在日志里找到它，确认字段是结构化的（不是 `[object Object]`）
- 打测试流量 → 确认指标序列出现了，label 符合预期、数值合理
- 在链路界面里跟一次跨服务请求 → 没有断掉的 span
- 每条新告警各触发一次（临时调低阈值）→ 确认它到了正确的通道，runbook 链接可用

## 常见自我合理化

| 合理化 | 现实 |
|---|---|
| 「先让它跑通，日志后面加」 | 「后面」会变成「第一次事故之后」，那是发现自己是瞎子最贵的时刻。边做边埋。 |
| 「日志越多越可观测」 | 非结构化的噪音只会让事故更慢。三条可查询的事件胜过三百行散文。 |
| 「先用 console.log 凑合」 | 非结构化输出没法筛选、没法关联、没法告警。结构化 logger 一次性也就多五分钟。 |
| 「出事的时候看板子就行」 | 没有定义问题就搭出来的看板，除了答案什么都有。从值班会问的问题出发。 |
| 「重要的都先告警，回头再调」 | 天天响的告警会训练人忽略它。调优永远不会发生，真正该叫的那次就漏了。 |
| 「用户 ID 当指标 label 更好查」 | 它也会把指标后端压垮。高基数查询属于日志和链路。 |
| 「就两个服务，上链路太重了」 | 两个服务就已经有了日志回答不了的跨服务延迟问题。自动埋点让成本几乎为零。 |

## 红旗

- 一个带重试、队列或外部调用的功能 PR，却没有任何新遥测
- 日志行用字符串拼接而不是结构化字段
- 没有关联 / 请求 ID —— 每行日志都是孤儿
- 同一份日志被调度器、webhook 和手工运行共同写入，却没有字段说明这行是谁产生的
- 指标 label 用了用户 ID、原始 URL 或错误信息文本（基数炸弹）
- 延迟只记平均值，没有百分位
- 天天触发、被人直接 ack 掉不处理的告警
- 对原因（CPU、内存）叫人，而面向用户的错误率没人监控
- 日志里出现密钥、token 或完整请求体
- 拿「我本地是好的」当作生产功能健康的唯一证据

## 验证

给一个功能埋完点之后，确认：

- [ ] 这个功能的值班问题已经写下来，每个信号都对应其中一个
- [ ] 所有日志输出都是结构化的（JSON），事件名稳定，每行都有关联 ID
- [ ] 由多个入口写入的每份日志都带入口点字段，在运行开始处设置，并与关联 ID 一起传播，而不是在下游推断
- [ ] 任何日志行里都没有密钥、token 或未脱敏的 PII（抽查真实输出）
- [ ] 每个新端点和每个外部依赖都有 RED 指标，label 集合有界
- [ ] 延迟是直方图，p95 / p99 可查
- [ ] 单个请求能在链路界面里端到端跟下去，没有断掉的 span
- [ ] 每条新告警都基于症状、带 runbook 链接，并且被测试触发过一次
- [ ] 在预发环境造的一个故障，能仅靠遥测定位，不用读源码
