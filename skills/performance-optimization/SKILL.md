# 性能优化

## 总览

先测量，再优化。没有测量的性能工作就是猜 —— 而猜会带来过早优化：增加复杂度，却没改善真正要紧的东西。先剖析，找出真正的瓶颈，修掉它，再测一遍。只优化测量证明重要的部分。

## 什么时候用

- 规格里有性能要求（加载时间预算、响应时间 SLA）
- 用户或监控报告慢
- Core Web Vitals 低于阈值
- 你怀疑某次改动引入了回归
- 在建处理大数据量或高流量的功能

**什么时候不用**：还没有问题证据时不要优化。过早优化加进来的复杂度，代价大于它换来的性能。

## Core Web Vitals 目标

| 指标 | 好 | 需改善 | 差 |
|------|-----|--------|-----|
| **LCP**（最大内容绘制） | ≤ 2.5s | ≤ 4.0s | > 4.0s |
| **INP**（交互到下次绘制） | ≤ 200ms | ≤ 500ms | > 500ms |
| **CLS**（累计布局偏移） | ≤ 0.1 | ≤ 0.25 | > 0.25 |

## 优化工作流

```
1. 测量 → 用真实数据建基线
2. 定位 → 找出真正的瓶颈（不是假设的）
3. 修   → 只改那一处瓶颈
4. 复测 → 再测一遍；保留或回退
5. 守门 → 加监控或测试，防回归
```

### 第 1 步：测量

两种互补手段，都要用：

- **合成测量（Lighthouse、开发者工具的 Performance 面板）：** 条件可控、可复现。适合 CI 回归检测和隔离具体问题。
- **RUM（web-vitals 库、CrUX）：** 真实用户、真实环境的数据。验证一次修复是否真的改善了用户体验，必须靠它。

**前端：**
```javascript
// 合成：Chrome 开发者工具里的 Lighthouse（或 CI）
// 开发者工具 → Performance 面板 → Record
// 也可以用 Luban 的 browser 工具打开页面，看 console / network / 渲染结果

// RUM：代码里接 web-vitals
import { onLCP, onINP, onCLS } from 'web-vitals';

onLCP(console.log);
onINP(console.log);
onCLS(console.log);
```

**后端：**
```javascript
// 响应时间日志
// 应用性能监控（APM）
// 带耗时的数据库查询日志

// 最朴素的计时
console.time('db-query');
const result = await db.query(...);
console.timeEnd('db-query');
```

### 先量哪里

用症状决定先量什么：

```
哪里慢？
├── 首次页面加载
│   ├── bundle 太大？→ 量 bundle 体积，检查代码分割
│   ├── 服务端响应慢？→ 在开发者工具 Network 瀑布图里看 TTFB
│   │   ├── DNS 耗时长？→ 对已知来源加 dns-prefetch / preconnect
│   │   ├── TCP/TLS 耗时长？→ 开 HTTP/2、检查边缘部署、keep-alive
│   │   └── 等待（服务端）耗时长？→ 剖析后端，检查查询与缓存
│   └── 有阻塞渲染的资源？→ 在瀑布图里找阻塞的 CSS/JS
├── 交互迟钝
│   ├── 点击后界面卡住？→ 剖析主线程，找长任务（>50ms）
│   ├── 表单输入延迟？→ 查重复渲染、受控组件的开销
│   └── 动画掉帧？→ 查布局抖动、强制重排
├── 跳转之后的页面
│   ├── 数据加载慢？→ 量 API 响应时间，找请求瀑布
│   └── 客户端渲染慢？→ 剖析组件渲染耗时，找 N+1 取数
└── 后端 / API
    ├── 单个端点慢？→ 剖析数据库查询，检查索引
    ├── 所有端点都慢？→ 查连接池、内存、CPU
    └── 间歇性变慢？→ 查锁竞争、GC 停顿、外部依赖
```

### 第 2 步：定位瓶颈

按类别看常见瓶颈：

**前端：**

| 症状 | 可能原因 | 怎么查 |
|------|---------|--------|
| LCP 慢 | 图片太大、阻塞渲染的资源、服务端慢 | 看网络瀑布图、图片体积 |
| CLS 高 | 图片没写尺寸、内容晚到、字体漂移 | 看布局偏移归因 |
| INP 差 | 主线程上有重 JS、大 DOM 更新 | 在 Performance 记录里找长任务 |
| 首屏加载慢 | bundle 大、请求多 | 看 bundle 体积、代码分割 |

**后端：**

| 症状 | 可能原因 | 怎么查 |
|------|---------|--------|
| API 响应慢 | N+1 查询、缺索引、查询未优化 | 看数据库查询日志 |
| 内存持续增长 | 引用泄漏、无界缓存、超大载荷 | 堆快照分析 |
| CPU 尖峰 | 同步重计算、正则回溯 | CPU 剖析 |
| 延迟高 | 缺缓存、重复计算、网络跳数 | 沿调用栈追踪请求 |

### 第 3 步：修那一处瓶颈

只改第 2 步定位出的那一件事，别的都别动。下面这些是常见病灶；每条给出规则和识别特征，具体改法见 [references/optimization-patterns.md](references/optimization-patterns.md)。需要时再打开对应那节。

**后端**

- **N+1 查询。** 每行一次查询是最常见的后端瓶颈。在同一条查询里把关联取出来（join / include），不要在循环里查。[模式](references/optimization-patterns.md#n1-queries-backend)
- **无界取数。** 每个列表端点都要分页，带 limit 和稳定的排序。[模式](references/optimization-patterns.md#unbounded-data-fetching)
- **查询没走索引。** 「加个索引」是猜，`EXPLAIN ANALYZE` 才是测量。你以为该走索引却是 `Seq Scan`、`rows=` 估算差一个数量级、扫描之上挂着 `Sort` 节点 —— 这三者对应的修法完全不同；`rows=` 估得离谱通常意味着统计信息过期，该跑 `ANALYZE` 而不是加索引。按查询形状建索引（等值列在前，再放范围或排序列）。普通索引救不了这几种情况：查询的是低选择性的主导值（该用部分索引服务稀有值）、前导通配符（需要三元组或全文索引）、列上套了函数（要建表达式索引，如 `WHERE lower(email) = ?`）。而且每个索引都在给每次写入加税。改完再跑一次执行计划；计划没变的索引就该回退。[模式](references/optimization-patterns.md#queries-that-ignore-their-index)
- **连接池耗尽。** 特征是：**所有**端点同时变慢，时间花在等连接而不是执行，数据库那边大多是空闲会话。一个进程一个池，大小按「实例数 × max」仍在数据库连接上限之内来定。池子更大不是更快，只是把队列挪到数据库那边，更难看清楚。实例数无界的场景（serverless、弹性伸缩）走代理多路复用（pgbouncer、RDS Proxy），而不是调大 `max`。[模式](references/optimization-patterns.md#connection-pool-exhaustion)
- **缺缓存。** 缓存那些「生成贵、读得远比写得频繁」的东西；给一条本来就很快的查询加缓存，只换来一次网络跳转和一个过期 bug。分层要主动选（进程内、共享、CDN）。任何会影响响应的输入都必须进 key（租户、语言、权限、feature flag）—— key 里漏掉「谁在看」，就是把一个用户的数据给了另一个。失效策略只选一种（TTL、事件或标签失效、版本化 key），并明确写出可接受的过期窗口。热门 key 要防击穿：一个请求重算、其余先拿旧值，或把并发的未命中合并到同一个在途请求后面。必须新鲜的东西永不缓存（余额、权限、结账时的库存）。[模式](references/optimization-patterns.md#missing-caching-backend)

**前端**

- **图片没优化。** 每张图都写 `width` 和 `height`（CLS）。LCP 那张图给 `fetchpriority="high"`，通过 `<picture>` 用现代格式（AVIF、WebP），用 `srcset`/`sizes` 做分辨率切换；首屏以下的图用 `loading="lazy"` 和 `decoding="async"`。[模式](references/optimization-patterns.md#missing-image-optimization-frontend)
- **不必要的重复渲染。** 渲染时创建的对象或函数每次都是新引用，会让接收它的每个子组件重渲。常量提到外面；`React.memo` 和 `useMemo` 只留给剖析证明开销大的地方 —— 用过头本身就是成本。[模式](references/optimization-patterns.md#unnecessary-re-renders-react)
- **bundle 太大。** 现代打包器自己就能对 ESM 具名导入做 tree-shaking；真正的大收益在路由级代码分割，以及把重而少用的功能放到 `Suspense` 后面懒加载。改 import 风格之前先剖析。[模式](references/optimization-patterns.md#large-bundle-size)

### 第 4 步：复测（保留还是回退）

在你复测之前，一次修复还只是个假设。这一步决定它能不能活下来。

**用建基线时的方式复测：** 同一条命令、同样的条件、同样固定的预算（墙钟时间、采样次数或请求数）。冷缓存下取的基线和热缓存下取的结果比，量的是缓存，不是你的改动。

**一次只改一个东西。** 三个优化一起落地只产出一个数字，你无法归因。如果它们必须一起发，先逐个单独测。

**要跑赢噪声，不只是均值。** 重复测量，把差值跟运行间波动比。±5% 波动里的 3% 提升不是提升，那只是另一个样本。

然后严格判定：

| 对比基线 | 动作 |
|---|---|
| 超过阈值、测试全绿 | **保留。** 提交信息里写清前后数字。 |
| 在噪声范围内（无可测变化） | **回退。** |
| 更差 | **回退。** |
| 有改善，但测试红了 | **回退。** 那是披着胜利外衣的回归。 |

**「中性」等于回退，不是保留。** 这一步最常被跳过：改动已经写完了，丢掉可惜，于是它未经测量就留了下来，代码库开始累积从未买到任何东西的复杂度。**留下的代码，你要永久维护。** 让它自己挣回成本。

**正确性给指标把关。** 测试套件保持绿 **且** 数字动了，才算数。靠削掉产品需要的工作换来的「优化」（跳过校验、缓存了必须新鲜的东西、删掉一个有承重作用的 `await`）是回归，不是胜利。

#### 每次尝试都记档，包括被回退的

被回退的工作在 git 历史里不留痕迹，这正是同一个死掉的点子在下一季度又被试一遍的原因。留一份短台账，让被否掉的点子保持被否掉：

| 点子 | 基线 → 结果 | 判定 | 原因 |
|---|---|---|---|
| 给行组件加 memo | INP 240ms → 235ms | 回退 | 在噪声内（±15ms）。行不是瓶颈。 |
| 列表虚拟化 | INP 240ms → 90ms | 保留 | 长任务从记录里消失了。 |
| 对 API 源站 preconnect | LCP 2.8s → 2.8s | 回退 | 本来就是同源。 |

写在 PR 描述里，或仓库里放一份 `PERF.md`，都行。关键是下一个人（或下一个 agent）提实验之前会读它，不会把已经失败过的再跑一遍。

### 第 5 步：防回归

守住用户真正能感觉到的那一个指标，不是所有能测的数。用它就是当初支撑这次修复的那个 LCP、INP、p95 延迟或别的主指标。

面向用户的面，用两层互补的守门：

- **合成 CI 门禁：** 用性能预算在合并前拦住可复现的回归。重复测量或比较中位数 / 趋势，别让正常的运行间波动把门禁变成时灵时不灵的检查。
- **线上监控：** RUM 数据里 p75 出现有意义的移动时告警。用带归因的 `web-vitals` 数据定位原因；CrUX 的滚动窗口当作确认，而不是即时告警。

任一守门报警，就回到第 1 步重新建基线，再提下一个修法。

**定预算并强制：**

```
JavaScript bundle：< 200KB（gzip，首屏）
CSS：< 50KB（gzip）
图片：每张 < 200KB（首屏范围内）
字体：合计 < 100KB
API 响应时间：< 200ms（p95）
4G 下可交互时间：< 3.5s
Lighthouse 性能分：≥ 90
```

**在 CI 里强制：**
```bash
# bundle 体积检查
npx bundlesize --config bundlesize.config.json

# Lighthouse CI。CLI 包名是 @lhci/cli；npm 上那个不带 scope 的 `lhci` 不是它。
npx --package=@lhci/cli lhci autorun
```

## 常见自我合理化

| 合理化 | 现实 |
|---|---|
| 「这个优化很明显」 | 没测过就不知道。先剖析。 |
| 「用户不会注意 100ms」 | 研究显示 100ms 的延迟会影响转化率。用户比你以为的敏感。 |
| 「框架会管性能」 | 框架能避免一些问题，但修不了 N+1 查询，也压不小过大的 bundle。 |
| 「查询慢，加索引」 | 先读执行计划。索引可能已经有了但用不上，而且每个索引都在永久给写入加税。 |
| 「加个缓存就行」 | 给本来便宜的调用加缓存什么也没买到，还添了个过期 bug。要缓存那些「贵 **且** 读远多于写」的。 |
| 「连接不够了，把池调大」 | 池子大于数据库能服务的量，只是把队列挪到了更看不见的地方。先找是谁占着连接。 |
| 「帮助不大，但也没坏处」 | 中性的改动就是回退。你会永久为它付维护费，却没换回任何东西。 |
| 「都写完了，留着吧」 | 沉没成本。测量不关心你写了多久。 |
| 「改善很明显，不用复测」 | 那复测很便宜，还能证明它。未经测量的「胜利」正是中性复杂度混进来的方式。 |

## 红旗

- 没有剖析数据支撑的优化
- 取数代码里存在 N+1 查询
- 加索引之前之后都没有执行计划来支撑
- 缓存 key 漏掉了响应所依赖的某个输入（租户、语言、看的人）
- 缓存没有写明过期窗口，也没有失效策略
- 连接池耗尽就调大池子，却没找是谁占着连接
- 列表端点没有分页
- 图片没有尺寸、没有懒加载、没有响应式尺寸
- bundle 体积增长却无人审
- 生产环境没有任何性能监控
- 到处 `React.memo` 和 `useMemo`（用过头和用不够一样糟）
- 保留了优化，却没有一次复测来支撑
- 多个优化捆在一次测量里，导致无法归因到单个改动
- 一个「胜利」是靠改掉、跳过或删掉某个测试换来的
- 同一个失败过的优化被反复尝试，因为没人记录第一次

## 验证

任何与性能相关的改动之后：

- [ ] 有改动前后的测量（具体数字）
- [ ] 结果是用建基线时同样的方式复测的（同命令、同条件）
- [ ] 改善超过了运行间波动，不只是超过均值
- [ ] 没跑赢基线的改动被回退了，没有当中性改动留下
- [ ] 尝试都有台账，保留与回退的都记，死掉的点子不会被重跑
- [ ] 具体瓶颈已定位并处理
- [ ] Core Web Vitals 落在「好」的阈值内
- [ ] bundle 体积没有明显增长
- [ ] 新的取数代码里没有 N+1 查询
- [ ] 任何新索引都有前后执行计划支撑，写入成本也考虑过
- [ ] 任何新缓存都写清了 key 是什么、怎么过期
- [ ] 被测量的用户可见指标有合成预算或线上监控，能发现回归
- [ ] 现有测试仍然通过（优化没改变行为）
