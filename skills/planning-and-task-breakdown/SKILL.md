# 计划与任务拆解

## 总览

把工作拆成小块的、可验证的任务，每个都带明确的验收标准。任务拆得好不好，决定 agent 是稳定地把活干完，还是产出一团乱麻。每个任务都应该小到能在一个专注的会话里实现、测试、验证完。

## 什么时候用

- 你有一份规格，需要把它落成可实现的单元
- 某个任务大到或虚到没法下手
- 工作要在多个 agent 或多个会话之间并行
- 你需要向人说明范围
- 实现顺序不明显

**什么时候不用**：范围清楚的单文件改动，或者规格里已经有定义良好的任务。

## 规划流程

### 第 1 步：进入只读模式

写任何代码之前，先只用读操作：

- 读规格和相关的代码区域
- 找出既有模式与约定
- 画出组件之间的依赖
- 记下风险与未知

**规划期间不要写代码。** 产物是一份计划文档（存到 `tasks/plan.md`）和一份任务清单（存到任务清单目标，见「产出文件」，默认 `tasks/todo.md`），不是实现。

Luban 里切到 Plan 模式更稳妥 —— 该模式下不能改文件，也不会误开下游工作。

### 第 2 步：画出依赖图

先把「谁依赖谁」画出来：

```
数据库 schema
    │
    ├── API 模型 / 类型
    │       │
    │       ├── API 端点
    │       │       │
    │       │       └── 前端 API client
    │       │               │
    │       │               └── UI 组件
    │       │
    │       └── 校验逻辑
    │
    └── 种子数据 / 迁移
```

实现顺序按依赖图自底向上：先把地基建好。

### 第 3 步：纵向切分

不是「先把整个数据库建完，再建所有 API，再建所有 UI」，而是一次交付一条完整的功能路径：

**坏的（横向切）：**
```
任务 1：建整个数据库 schema
任务 2：建所有 API 端点
任务 3：建所有 UI 组件
任务 4：把一切连起来
```

**好的（纵向切）：**
```
任务 1：用户能注册（注册相关的 schema + API + UI）
任务 2：用户能登录（鉴权 schema + API + UI）
任务 3：用户能新建任务（任务 schema + API + UI）
任务 4：用户能看任务列表（查询 + API + 列表页 UI）
```

每条纵向切片都交付能跑、能测的功能。

### 第 4 步：写任务

每个任务都按这个结构写 —— 无论是落到 markdown 任务清单，还是外部跟踪工具（见「产出文件」）：

```markdown
## 任务 [N]：[简短的描述性标题]

**描述：** 一段话说明这个任务要达成什么。

**验收标准：**
- [ ] [具体、可测的条件]
- [ ] [具体、可测的条件]

**验证：**
- [ ] 测试通过：[本仓的聚焦测试命令]
- [ ] 构建成功：[本仓的构建命令]
- [ ] 人工确认：[要核对什么]

**依赖：** [依赖的任务编号，或「无」]

**可能改动的文件：**
- `src/path/to/file.ts`
- `tests/path/to/test.ts`

**估计规模：** [小：1-2 个文件 | 中：3-5 个文件 | 大：5+ 个文件]
```

### 第 5 步：排序与检查点

把任务排成满足这些条件的顺序：

1. 依赖已满足（先建地基）
2. 每个任务结束时系统都处于可工作状态
3. 每 2-3 个任务后有一个验证检查点
4. 高风险任务排前面（早失败早发现）

把检查点明确写进任务清单：

```markdown
## 检查点：任务 1-3 之后
- [ ] 所有测试通过
- [ ] 应用构建无错误
- [ ] 核心用户流程端到端可用
- [ ] 与人确认后再继续
```

## 任务粒度参考

| 规模 | 文件数 | 范围 | 例子 |
|------|-------|------|------|
| **XS** | 1 | 单个函数或配置改动 | 加一条校验规则 |
| **S** | 1-2 | 一个组件或一个端点 | 加一个新 API 端点 |
| **M** | 3-5 | 一条功能切片 | 用户注册流程 |
| **L** | 5-8 | 跨组件的功能 | 带筛选与分页的搜索 |
| **XL** | 8+ | **太大了 —— 继续拆** | — |

任务是 L 或更大，就该继续拆。agent 在 S 和 M 的任务上表现最好。

**该进一步拆的信号：**
- 它做不完一个专注会话（大约 2 小时以上的 agent 工作时间）
- 验收标准你写不出三条以内的要点
- 它同时碰两个互相独立的子系统（比如鉴权和计费）
- 任务标题里出现了「和」或者「以及」（那就是两个任务）

## 产出文件

- **计划文档：** 实现计划存到 `tasks/plan.md`。这一份永远是 markdown —— 设计决定、风险、待定问题这些东西塞不进单个工单。
- **任务清单：** 每个任务记到**任务清单目标**（见下）。

`tasks/` 目录不存在就建。

**绝不覆盖未完成的计划。** 写 `tasks/plan.md` 或 `tasks/todo.md` 之前，先看它们是否已存在且还有未勾选的任务：

- 同一件事重新规划（用户要求修改或扩展这份计划）→ 就地更新现有文件。
- 不同的事 → **停下来问。** 那些未勾选的任务可能正在另一个会话里做。不要自行删除、覆盖或改名现有文件；把冲突摆出来让用户决定（先做完旧计划、明确丢弃旧计划、或者指定新计划该放哪）。

同样的规则也适用于外部跟踪工具：不要为了腾地方就批量关掉或删掉另一份计划里还开着的条目。

### 任务清单目标

任务清单目标是任务与检查点记录的地方。它只在这里定义一次，本技能其他提到的地方都以它为准。

- **默认：`tasks/todo.md` 里的清单式 markdown 文件。** 下游流程默认按这个约定找文件。除非项目另有规定，就用它。
- **外部跟踪工具：** 如果项目的 agent 规则（`AGENTS.md`、`.luban/rules` 等）或用户指定了工单系统（GitHub Issues、Jira、Linear、beads 等），就一个任务建一个工单，而不是写 `tasks/todo.md`。把第 4 步的结构映射到工单字段上：验收标准与验证步骤写进工单正文，依赖用工具自己的关联机制（`blocked by` 等）。第 5 步的检查点也建成工单，或者如果工具没有对应物，就写成计划文档里的清单。

用外部跟踪工具时，在 `tasks/plan.md` 里注明（例如「任务跟踪在 Linear 项目 FOO」），让下游步骤和后续会话知道去哪找；计划文档的「任务清单」一节保留为工单 id 或链接的有序索引，不要复制成第二份清单。

## 计划文档模板

```markdown
# 实现计划：[功能/项目名]

来源规格：[本计划依据的规格路径，如 SPEC.md 或 SPEC-<change>.md；没有就省略]

## 总览
[一段话说明我们在建什么]

## 架构决定
- [关键决定 1 及理由]
- [关键决定 2 及理由]

## 任务清单

### 阶段 1：地基
- [ ] 任务 1：...
- [ ] 任务 2：...

### 检查点：地基
- [ ] 测试通过、构建干净

### 阶段 2：核心功能
- [ ] 任务 3：...
- [ ] 任务 4：...

### 检查点：核心功能
- [ ] 端到端流程可用

### 阶段 3：收尾
- [ ] 任务 5：...
- [ ] 任务 6：...

### 检查点：完成
- [ ] 所有验收标准满足
- [ ] 可以评审

## 风险与应对
| 风险 | 影响 | 应对 |
|------|------|------|
| [风险] | [高/中/低] | [策略] |

## 待定问题
- [需要人回答的问题]
```

任务放在外部跟踪工具时，「任务清单」一节保留为工单 id 或链接的有序索引，别再写一份清单。

## 可并行的部分

有多个 agent 或多个会话可用时：

- **可以并行：** 互相独立的功能切片、已经实现的功能的测试、文档
- **必须串行：** 数据库迁移、共享状态改动、依赖链上的任务
- **需要协调：** 共用同一份 API 契约的功能 —— 先把契约定下来，再并行

## 常见自我合理化

| 合理化 | 现实 |
|---|---|
| 「边做边想吧」 | 这正是最后得到一团乱麻和返工的原因。10 分钟规划省掉几小时。 |
| 「任务很明显」 | 还是写下来。写出来的任务会暴露隐藏依赖和被忘掉的边界情况。 |
| 「规划是额外开销」 | 规划就是活。没有计划的实现只是在打字。 |
| 「这些我脑子里都装得下」 | 上下文窗口是有限的。写下来的计划能跨会话、跨上下文压缩活下来。 |
| 「旧的 `tasks/plan.md` 过期了，直接替换吧」 | 那些未勾选的任务可能正在另一个会话里做。覆盖会毁掉一份别处不存在的进度状态。停下来问。 |

## 红旗

- 没有书面任务清单就开始实现
- 在没有征询的情况下，覆盖掉还有未勾选任务的 `tasks/plan.md` 或 `tasks/todo.md`
- 项目已经指定外部跟踪工具，却还在写 `tasks/todo.md`（或者两边都撒）
- 任务只写「实现这个功能」，没有验收标准
- 计划里没有验证步骤
- 所有任务都是 XL 规模
- 任务之间没有检查点
- 完全没考虑依赖顺序

## 验证

开始实现之前，逐条确认：

- [ ] 每个任务都有验收标准
- [ ] 每个任务都有验证步骤
- [ ] 任务依赖已识别且排序正确
- [ ] 任务已记到任务清单目标（默认 `tasks/todo.md`）
- [ ] 没有在未经用户明确确认的情况下覆盖任何未完成的旧计划
- [ ] 没有任务碰超过约 5 个文件
- [ ] 主要阶段之间有检查点
- [ ] 人已经评审并批准了计划
