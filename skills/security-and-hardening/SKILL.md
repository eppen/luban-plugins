# 安全与加固

## 总览

Web 应用的安全优先开发实践。把每个外部输入都当成敌意的，把每个密钥都当成神圣的，把每个授权检查都当成必做项。安全不是一个阶段，而是每一行接触用户数据、鉴权或外部系统的代码都要满足的约束。

## 什么时候用

- 做任何接受用户输入的东西
- 实现认证或授权
- 存储或传输敏感数据
- 集成外部 API / 服务
- 加文件上传、webhook 或回调
- 处理支付或个人身份信息（PII）

## 流程：先做威胁建模

没有威胁模型就往上装的防护措施，全是猜的。加固之前，花五分钟像攻击者一样想一遍：

1. **画出信任边界。** 不可信数据从哪进入系统？HTTP 请求、表单字段、文件上传、webhook、第三方 API、消息队列，以及 **LLM 输出** —— 还有那些看着像「内部值」、其实是操作系统转手给你的东西：别的进程的命令行或环境变量、共享卷上的文件名、任务载荷里的路径。**信任跟着「谁写的」走，不跟着「哪个通道送来的」走。** 每条边界都是攻击面。
2. **点名资产。** 什么值得偷、值得破坏？凭据、PII、支付数据、管理操作、资金流动。
3. **对每条边界跑一遍 STRIDE** —— 是快速透镜，不是仪式：

| 威胁 | 问什么 | 常见缓解 |
|---|---|---|
| **S**poofing 冒充 | 有人能假冒用户 / 服务吗？ | 认证、签名校验 |
| **T**ampering 篡改 | 数据在传输或存储中能被改吗？ | 完整性校验、参数化查询、HTTPS |
| **R**epudiation 抵赖 | 某个操作事后能被否认吗？ | 安全事件审计日志 |
| **I**nformation disclosure 泄露 | 数据会外泄吗？ | 加密、字段白名单、通用错误 |
| **D**enial of service 拒绝服务 | 能被打爆吗？ | 限流、输入大小上限、超时 |
| **E**levation of privilege 提权 | 用户能拿到不该有的权限吗？ | 授权检查、最小权限 |

4. **在用例旁边写滥用用例。** 每个功能都问一句「我要怎么滥用它？」—— 然后把那个当成第一个测试。

如果你连一个功能的信任边界都点不出来，就还没到能做安全的时候。这是 OWASP **A06:2025 不安全设计** —— 多数事故始于设计，而不是代码。

## 三档边界规则

### 总是做（没有例外）

- **校验所有外部输入**，在系统边界（API 路由、表单处理器）
- **数据库查询全部参数化** —— 绝不把用户输入拼进 SQL
- **输出编码**，防 XSS（用框架的自动转义，不要绕过它）
- **所有对外通信走 HTTPS**
- **密码用 bcrypt / scrypt / argon2 哈希**（绝不存明文）
- **设置安全响应头**（CSP、HSTS、X-Frame-Options、X-Content-Type-Options）
- **会话 cookie 用 httpOnly、secure、sameSite**
- **每次发版前，用项目检测出的包管理器对已提交的 lockfile 跑原生审计**

### 先问再做（需要人批准）

- 新增认证流程或改动鉴权逻辑
- 存储新类别的敏感数据（PII、支付信息）
- 新增外部服务集成
- 改动 CORS 配置
- 新增文件上传处理器
- 修改限流 / 节流配置
- 授予更高权限或角色

### 绝不做

- **绝不把密钥提交进版本控制**（API key、密码、token）
- **绝不记录敏感数据**（密码、token、完整卡号）
- **绝不把客户端校验当成安全边界**
- **绝不为了方便关闭安全头**
- **绝不对用户提供的数据用 `eval()` 或 `innerHTML`**
- **绝不把会话放进客户端可访问的存储**（用 localStorage 存鉴权 token）
- **绝不向用户暴露堆栈或内部错误细节**

## 加固要点

下面是工作流；每一项的具体实现见 [references/hardening-patterns.md](references/hardening-patterns.md)。需要哪节再打开哪节，别提前全读。

### 注入与 XSS

- 所有 SQL 走参数化查询或 ORM 的绑定参数，绝不字符串拼接。原生查询同样适用。
- 用户内容渲染进 HTML 时用框架的自动转义；确实需要富文本，就用可靠的净化库并配 CSP。
- 每个受保护对象都要**归属校验**：不仅检查「登录了吗」，还要检查「这个资源是不是他的」。别用自增 id 猜资源（A01:2025，IDOR）。

模式：[注入](references/hardening-patterns.md#injection)、[XSS](references/hardening-patterns.md#cross-site-scripting-xss)、[访问控制](references/hardening-patterns.md#broken-access-control)。

### 认证与会话

- 密码用 bcrypt（≥12 轮）、scrypt 或 argon2 哈希。会话密钥来自环境变量，绝不写在代码里。
- 会话 cookie 设 `httpOnly`、`secure`、`sameSite: 'lax'` 或 `'strict'`（这是 CSRF 防护；`'none'` 会让 cookie 跨站发送），并设有限的 `maxAge`。

模式：[认证](references/hardening-patterns.md#broken-authentication)。

### 响应头、CORS 与响应体

- 每个响应都带安全头（helmet 或框架等价物）；CSP 从 `default-src 'self'` 起步，只会收紧不会放松。
- CORS 限定在配置里的明确来源列表。带凭据时绝不用 `*`。
- 返回之前剥掉敏感字段（`passwordHash`、重置 token）。错误体写通用信息，内部细节只进服务端日志。

模式：[错误配置](references/hardening-patterns.md#security-misconfiguration)、[敏感数据泄露](references/hardening-patterns.md#sensitive-data-exposure)。

### 输入校验与上传

- 在边界用 schema 校验：形状白名单、长度、枚举、格式。不合法就回 422 和结构化细节；下游代码只用解析后的、带类型的值。
- 上传：MIME 类型白名单、大小上限，必要时校验内容（magic bytes）。扩展名什么也证明不了。

模式：[schema 校验](references/hardening-patterns.md#schema-validation-at-boundaries)、[文件上传](references/hardening-patterns.md#file-upload-safety)。

### 服务端抓取（SSRF）

任何用户能影响的 URL —— webhook、从 URL 导入、图片代理、链接预览 —— 都可能被指向内部服务。白名单限制协议和主机，解析**全部** DNS 记录并拒绝任何私有或保留地址（回环、链路本地 `169.254.169.254`、私有网段、唯一本地地址，IPv4 与 IPv6 都要管），并禁止重定向。这个检查仍然留着 DNS 重绑定的 TOCTOU 缺口：高风险面要么钉住解析后的 IP，要么在前面放一层过滤代理。

模式：[SSRF](references/hardening-patterns.md#server-side-request-forgery-ssrf)。

### 派生路径上的破坏性操作

一次删除、移动或覆盖的安全程度，取决于「谁写了那个目标路径」—— **信任跟着写值的人走**，不跟着通道走：别的进程的命令行和表单字段一样是攻击者可控的。形状检查只能证明格式合法，证明不了授权。调用之前必须同时满足三条：解析后的目标（符号链接已解开）位于**白名单根**之下；它在该根下**至少低一层**；它带有**操作前读取到的归属证据**。被拒时记录被拒的目标并停下，绝不回退到更宽的默认路径。

为什么这个检查比看起来更弱（标记自证、检查/使用竞态）：见 [破坏性路径](references/hardening-patterns.md#destructive-operations-on-derived-paths)。完整代码示例见本技能的 `references/security-checklist.md`。

### 限流

API 整体限流，认证端点严格限流（约 15 分钟 10 次尝试）。一旦有一个以上进程在服务流量，内存计数器就会悄悄变成 `上限 × 实例数`，在 serverless 上则可能永远不触发：用共享存储做限流器的后端。

模式：[限流](references/hardening-patterns.md#rate-limiting)。

### 密钥

密钥来自环境。`.env.example` 可以提交（只放占位符）；真正的 `.env*` 和密钥材料必须进 `.gitignore`；提交前 grep 一遍暂存区。**密钥一旦到了远端就算泄露：先轮换，再清历史。**

模式：[密钥管理](references/hardening-patterns.md#secrets-management)。

### 依赖与供应链

1. **先找准安装边界和管理器。** 用持有 lockfile 的工作区根；只有当某个嵌套项目在该工作区之外时，才把它当独立项目。用 `packageManager` 字段（有的话）、lockfile、CI 三者交叉印证；出现不一致或多个竞争 lockfile 就停下。钉住管理器版本。
2. **首次执行前先拦住依赖脚本。** 以禁用脚本或明确的 fail-closed 策略引导安装，检查待执行的脚本源码，只批准最低限度，把策略提交进仓，再用干净的 frozen / immutable 安装验证一遍。绝不一把全批准。
3. **每次发版前对已提交的 lockfile 跑原生审计。** 按**可达性**（运行时、构建、测试、部署路径）分诊 critical / high，并看有没有可用修复。绝不自动执行强制修复（`npm audit fix --force` 之类），因为强制修复可能跨出声明的依赖范围；先预览、读 changelog、逐个升级并测试。每个暂缓项都写下原因和复查日期。
4. **审计只匹配已知公告。** 它抓不到新出现的恶意包或仿冒包（`cross-env` vs `crossenv`）。新依赖、lockfile 差异、脚本策略变更要一起评审：归属、维护活跃度、发布时长、来源、传递依赖图。支持时校验注册源签名（`npm audit signatures`、`pnpm audit signatures`），没有签名是「去查」的信号，不是自动的入侵结论（A03:2025、LLM03）。

分诊决策树：[依赖审计分诊](references/hardening-patterns.md#dependency-audit-triage)。管理器矩阵与安装脚本闸门见本技能的 `references/security-checklist.md`。

### 个人信息与隐私

加固问的是「攻击者能读到吗」，隐私问的是「我们**该不该**持有它、持有多久」。最省钱的数据是从未采集过的数据；把个人信息当成负债来最小化。

- **加字段时就分类**（非个人、PII、敏感），按类别分别处理。你找不到的数据，既保护不了，也履行不了删除请求。
- **只为明确目的采集。** 「以后可能有用」是潜在的泄露面，不是目的。PII 不要进遥测（`observability-and-instrumentation` 从运维角度说的是同一件事）。
- **先定留存期限，然后真的删。** 每个个人信息存储都要有 TTL 和能用的删除路径，包括备份、缓存、搜索索引和分析副本。
- **支持所在辖区要求的数据主体权利**（GDPR、CCPA 及同类）：导出、更正、删除。schema 设计要让某个用户的数据可被找到、可被抹掉，而不是不可逆地抹散在十个系统里。
- **同意是采集与第三方共享的前置条件，而且要可审计。** 把 PII 发给分析、广告或 LLM 供应商就是共享；供应商需要有数据处理协议。地区要作为可配置策略，不是硬编码假设。

分类表：[数据分类](references/hardening-patterns.md#data-classification)。隐私事故会启动泄露通报的计时器；复盘用 `debugging-and-error-recovery`。

### AI / LLM 特性

调用 LLM —— 聊天、摘要、agent、RAG —— 等于新增一块攻击面，按 [OWASP LLM 应用十大风险（2025）](https://genai.owasp.org/llm-top-10/) 来映射：

- **模型输出是不可信输入**（LLM05）。绝不直接进 `eval`、SQL、shell、`innerHTML` 或文件路径；先防御性解析，再按 schema 校验，再编码。
- **提示词可能被劫持**（LLM01）。上下文里的不可信文本 —— 用户消息、抓来的网页、PDF —— 都可能携带指令。系统提示词不是安全边界；权限必须在代码里强制。
- **密钥、其他租户的数据、完整系统提示词不进上下文窗口**（LLM02、LLM07）；收窄工具权限、校验每个工具参数，破坏性操作要二次确认（LLM06）；给 token、请求速率和递归深度设上限。

模式：[LLM 特性](references/hardening-patterns.md#ai--llm-features)。

## 常见自我合理化

| 合理化 | 现实 |
|---|---|
| 「内部工具，不用管安全」 | 内部工具照样被打穿。攻击者专挑最弱的一环。 |
| 「安全以后再加」 | 事后补安全的成本是内建的 10 倍。现在就加。 |
| 「没人会来打这个」 | 自动化扫描器会找到它。靠隐蔽不是安全。 |
| 「框架会处理安全」 | 框架提供工具，不提供保证。你还是得用对。 |
| 「就是个原型」 | 原型会变成生产。从第一天就养成安全习惯。 |
| 「做威胁建模太重了」 | 五分钟的「我要怎么打这个」，能防住之后任何控制措施都补不上的设计缺陷。 |
| 「LLM 输出而已，就是点文字」 | 那段「文字」可能是一条 SQL、一个 script 标签或一条 shell 命令。按不可信输入处理。 |
| 「审计过了，依赖没问题」 | 审计只匹配已知公告。它发现不了新出现的恶意包，也不能让未经评审的安装脚本变安全。 |
| 「先采集着，以后可能有用」 | 你没持有的数据不会被泄露、不会被传票调取、也不会被误删。「可能有用」是泄露面，不是目的。 |
| 「删除请求我们手工处理就行」 | 手工删除会漏掉备份、缓存和分析副本。schema 找不到某个用户的数据，你就履行不了请求 —— 要为此设计。 |
| 「合规是法务的事，不是我们的」 | 导出、删除、留存、同意都是 schema 和代码。等你把 PII 抹散在十个系统里，法务也补不上。 |

## 红旗

- 用户输入直接进了数据库查询、shell 命令或 HTML 渲染
- 删除 / 移动 / 覆盖的目标来自载荷、配置值或别的进程命令行，却只做了一次路径形状检查
- 源码或提交历史里有密钥
- API 端点没有认证或授权检查
- CORS 没配，或用了通配 `*`
- 认证端点没有限流，或者多个实例前面挂的却是内存限流器
- 把堆栈或内部错误暴露给用户
- 依赖有已知 critical 漏洞、同一安装边界下存在竞争 lockfile、安装不可复现，或安装脚本被一把全批准
- 服务端抓取用户给的 URL 而不做白名单（SSRF）
- LLM / 模型输出被塞进查询、DOM、shell 或 `eval`
- 密钥、PII 或完整系统提示词被放进了 LLM 上下文窗口
- 采集个人信息却没有明确目的、留存上限或删除路径
- 把 PII 发给分析 / 广告 / LLM 供应商，却没有同意和数据处理协议
- 「删除我的账号」只是翻了个 flag，个人数据还留在各处存储和备份里

## 验证

实现完与安全相关的代码之后：

- [ ] 原生审计没有未处理的可达 critical / high 项；CI 保住权威 lockfile 并拦截未经评审的依赖脚本
- [ ] 源码和 git 历史里都没有密钥
- [ ] 所有用户输入在系统边界完成校验
- [ ] 破坏性的文件系统操作先解开符号链接，再验证白名单根、最小深度和归属，然后才执行
- [ ] 每个受保护端点都做了认证与授权检查
- [ ] 响应里带安全头（用浏览器开发者工具核对）
- [ ] 错误响应不暴露内部细节
- [ ] 认证端点有限流，多实例时后端是共享存储
- [ ] 服务端抓取 URL 都过了白名单校验（无 SSRF）
- [ ] LLM / 模型输出在用之前已校验并编码（如果产品有 AI 特性）
- [ ] 个人信息已分类、按明确目的最小化，并有留存上限
- [ ] 删除与导出请求端到端可用（含备份、缓存和分析副本）
