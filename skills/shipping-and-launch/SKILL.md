# 发布与上线

## 总览

带着把握上线。目标不只是部署成功，而是**安全地**部署：监控就位、回滚方案备好、清楚知道成功长什么样。每次上线都应当是可回滚的、可观测的、增量的。

## 什么时候用

- 首次把功能部署到生产
- 向用户发布较大改动
- 迁移数据或基础设施
- 开内测 / 早期访问
- 任何带风险的部署（也就是所有部署）

## 上线前清单

### 代码质量

- [ ] 所有测试通过（单元、集成、端到端）
- [ ] 构建成功且无告警
- [ ] lint 与类型检查通过
- [ ] 代码已评审通过
- [ ] 没有该在上线前清掉的 TODO
- [ ] 生产代码里没有 `console.log` 调试语句
- [ ] 错误处理覆盖了预期的失败模式

### 安全

- [ ] 代码与版本控制里没有密钥
- [ ] 生态自带的依赖审计（`npm audit`、`pip-audit`、`cargo audit`……）没有 critical / high
- [ ] 所有面向用户的端点都做输入校验
- [ ] 认证与授权检查就位
- [ ] 安全响应头已配置（CSP、HSTS 等）
- [ ] 认证端点有限流
- [ ] CORS 限定具体来源（不是通配）

### 性能

- [ ] Core Web Vitals 在「好」的阈值内
- [ ] 关键路径上没有 N+1 查询
- [ ] 图片已优化（压缩、响应式尺寸、懒加载）
- [ ] bundle 体积在预算内
- [ ] 数据库查询有合适的索引
- [ ] 静态资源和重复查询已配缓存

### 可访问性

- [ ] 所有可交互元素都能键盘操作
- [ ] 屏幕阅读器能读出页面内容与结构
- [ ] 对比度满足 WCAG 2.1 AA（正文 4.5:1）
- [ ] 弹窗与动态内容的焦点管理正确
- [ ] 错误信息清楚，且与表单字段关联
- [ ] axe-core 或 Lighthouse 里没有可访问性告警

### 基础设施

- [ ] 生产环境变量已设置
- [ ] 数据库迁移已执行（或已就绪待执行）
- [ ] DNS 与 SSL 已配置
- [ ] 静态资源的 CDN 已配置
- [ ] 日志与错误上报已配置
- [ ] 健康检查端点存在且能响应

### 文档

- [ ] README 已更新新增的搭建要求
- [ ] API 文档是最新的
- [ ] 架构决定都写了 ADR
- [ ] 变更日志已更新
- [ ] 面向用户的文档已更新（如适用）

## Feature flag 策略

放在开关后面发布，把「部署」和「发布」解耦：

```typescript
// 读开关
const flags = await getFeatureFlags(userId);

if (flags.taskSharing) {
  // 新功能：任务分享
  return <TaskSharingPanel task={task} />;
}

// 默认：既有行为
return null;
```

**开关生命周期：**

```
1. 带开关（关）部署   → 代码在生产但未生效
2. 对团队 / 内测打开   → 在生产环境做内部测试
3. 逐步放量           → 5% → 25% → 50% → 100% 用户
4. 每一档都监控        → 看错误率、性能、用户反馈
5. 清理               → 全量之后删掉开关和死代码路径
```

**规则：**
- 每个开关都有负责人和过期时间
- 全量后两周内清理
- 不要嵌套开关（组合数指数爆炸）
- CI 里两种状态都要测（开和关）

## 分阶段放量

### 放量顺序

```
1. 部署到预发
   └── 在预发跑全量测试
   └── 对关键流程做人工冒烟

2. 部署到生产（开关关）
   └── 确认部署成功（健康检查）
   └── 看错误监控（没有新错误）

3. 对团队打开（内部用户开关开）
   └── 团队在生产环境用这个功能
   └── 24 小时观察窗口

4. 金丝雀放量（5% 用户开关开）
   └── 监控错误率、延迟、用户行为
   └── 对比指标：金丝雀 vs 基线
   └── 24-48 小时观察窗口
   └── 所有阈值都过才继续（见下表）

5. 逐步提高（25% → 50% → 100%）
   └── 每一步同样监控
   └── 任何时刻都能退回上一档比例

6. 全量（所有用户开关开）
   └── 观察一周
   └── 清理 feature flag
```

### 放量决策阈值

每一档用这些阈值决定「继续 / 暂停排查 / 回滚」：

| 指标 | 继续（绿） | 暂停排查（黄） | 回滚（红） |
|------|-----------|---------------|-----------|
| 错误率 | 基线 ±10% 以内 | 高于基线 10-100% | 超过基线 2 倍 |
| P95 延迟 | 基线 ±20% 以内 | 高于基线 20-50% | 高于基线 50% 以上 |
| 客户端 JS 错误 | 没有新错误类型 | 新错误出现在 <0.1% 会话 | 新错误出现在 >0.1% 会话 |
| 业务指标 | 持平或正向 | 下降 <5%（可能是噪声） | 下降 >5% |

### 什么时候回滚

出现下列情况立刻回滚：
- 错误率超过基线 2 倍
- P95 延迟上升超过 50%
- 用户报告的问题激增
- 发现数据完整性问题
- 发现安全漏洞

## 监控与可观测

### 监控什么

```
应用指标：
├── 错误率（总量与按端点）
├── 响应时间（p50、p95、p99）
├── 请求量
├── 活跃用户
└── 关键业务指标（转化、活跃度）

基础设施指标：
├── CPU 与内存利用率
├── 数据库连接池使用率
├── 磁盘空间
├── 网络延迟
└── 队列深度（如适用）

客户端指标：
├── Core Web Vitals（LCP、INP、CLS）
├── JavaScript 错误
├── 从客户端视角看到的 API 错误率
└── 页面加载时间
```

### 错误上报

```typescript
// 错误边界 + 上报
class ErrorBoundary extends React.Component<React.PropsWithChildren> {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    // 上报到错误跟踪服务
    reportError(error, {
      componentStack: info.componentStack,
      userId: getCurrentUser()?.id,
      page: window.location.pathname,
    });
  }

  render() {
    if (this.state.hasError) {
      return <ErrorFallback onRetry={() => this.setState({ hasError: false })} />;
    }
    return this.props.children;
  }
}

// 服务端错误上报
app.use((err: Error, req: Request, res: Response, next: NextFunction) => {
  reportError(err, {
    method: req.method,
    url: req.url,
    userId: req.user?.id,
  });

  // 不把内部细节暴露给用户
  res.status(500).json({
    error: { code: 'INTERNAL_ERROR', message: '出错了' },
  });
});
```

### 上线后核对

上线后第一个小时：

```
1. 健康检查端点返回 200
2. 看错误监控看板（没有新错误类型）
3. 看延迟看板（没有回归）
4. 手工走一遍关键用户流程
5. 确认日志在流动、可读
6. 确认回滚机制可用（能演练就演练一次）
```

## 错误预算发布门禁

服务的错误预算 —— SLO 允许失败的那部分请求或时间 —— 决定现在发布是否安全。把它当成客观门禁，不是谈判：

```
剩余预算 > 20%  →  正常发布；密切监控
剩余预算 0–20%  →  只能慢速放量；不做高风险改动
预算耗尽        →  冻结功能开发；全力做可靠性
预算重置        →  恢复正常节奏；把恢复它的修复固化下来
```

金丝雀期间烧钱率很高（消耗预算比基线更快）在上面那张放量表里是**暂停**信号 —— 和错误率升高同等对待。

## 回滚策略

每次部署之前都要先有回滚方案：

```markdown
## [功能/版本] 的回滚方案

### 触发条件
- 错误率超过基线 2 倍
- P95 延迟超过 [X]ms
- 用户反馈 [具体问题]

### 回滚步骤
1. 关掉 feature flag（如适用）
   或
1. 部署上一版本：`git revert <commit> && git push`
2. 验证回滚：健康检查、错误监控
3. 同步信息：通知团队已回滚

### 数据库相关
- 迁移 [X] 有回滚路径：<已验证的命令或 runbook 链接>
- 新功能写入的数据：[保留 / 清理]

### 回滚耗时
- 关开关：< 1 分钟
- 重新部署上一版本：< 5 分钟
- 数据库回滚：< 15 分钟
```

## 常见自我合理化

| 合理化 | 现实 |
|---|---|
| 「预发能跑，生产也能跑」 | 生产的 数据、流量模式、边角情况都不一样。部署之后要盯着。 |
| 「这个功能不需要开关」 | 每个功能都受益于一个总闸。再「简单」的改动也可能弄坏东西。 |
| 「监控是额外开销」 | 没有监控，你就只能从用户投诉里发现问题，而不是从看板。 |
| 「监控回头再加」 | 上线前就加。看不见的东西你调试不了。 |
| 「回滚等于承认失败」 | 回滚是负责任的工程。把坏功能发出去才是失败。 |
| 「错误率看着还行，继续发」 | 看烧钱率，不只看当前错误率。消耗预算快于基线，即使单项阈值是绿的也是暂停信号。 |

## 红旗

- 没有回滚方案就部署
- 生产环境没有监控或错误上报
- 一次性大爆炸发布（全量上，没有预发）
- feature flag 没有过期时间也没有负责人
- 上线后第一个小时没人盯着
- 生产环境配置靠记忆改，不靠代码
- 「都周五下午了，发吧」
- 错误预算已耗尽，功能开发照旧

## 验证

部署之前：

- [ ] 上线前清单已完成（各部分全绿）
- [ ] feature flag 已配置（如适用）
- [ ] 回滚方案已成文
- [ ] 监控看板已就位
- [ ] 已通知团队要部署

部署之后：

- [ ] 健康检查返回 200
- [ ] 错误率正常
- [ ] 延迟正常
- [ ] 关键用户流程可用
- [ ] 日志在流动
- [ ] 回滚已演练，或确认处于可用状态

每交付一个服务：

- [ ] 有错误预算政策：预算掉到 20% 以下该怎么做、耗尽时该怎么做，都写清楚了
