# 规格驱动开发

## 总览

写任何代码之前，先写一份结构化的规格。规格是你和人类工程师之间的共同事实源 —— 它定义我们在做什么、为什么做、怎么算做完。没有规格的代码就是在猜。

## 什么时候用

- 开新项目或新功能
- 需求含糊或不完整
- 改动横跨多个文件或模块
- 你正准备做一个架构决定
- 这事实现起来要超过 30 分钟

**什么时候不用**：单行修复、改错别字、需求无歧义且自洽的小改动。

## 带门禁的流程

规格驱动开发有四个阶段，前面还有一个范围检查（Phase 0）—— 只有当一次请求里捆了好几个可独立验证的能力时才启用。当前阶段没过确认，就不要进下一阶段。

```
规格 ──→ 计划 ──→ 任务 ──→ 实现
  │        │        │        │
  ▼        ▼        ▼        ▼
人工      人工      人工      人工
确认      确认      确认      确认
```

### Phase 0：范围检查

大多数请求只描述一个能力。是这种情况就直接跳到「规格」，别走这一阶段 —— Phase 0 是为例外准备的，不是常规流程，也不给单能力功能强加层级。

**怎么判断。** 一个需求里捆了好几个可独立验证的能力时，先拆再写规格：

- 需求里点名了几个各有自己使用方或数据的能力（如账号、计费、通知、报表）
- 验收标准能聚成几组，可以各自上线、各自验证
- 其中一个能力被砍掉或替换，其他能力的要求不用重写

**写任何规格之前，先提一份能力地图。** 要小而可评审 —— 一张模块表加一个建设顺序，不是项目计划：

```markdown
# 能力地图：[项目名]

| 模块 id | 职责 | 依赖 |
|---|---|---|
| identity | 账号、会话、SSO | — |
| billing | 套餐、发票、支付 | identity |
| notifications | 邮件与 webhook 分发 | identity |
| reporting | 用量报表 | billing, notifications |

建设顺序：identity → billing, notifications → reporting
```

- **模块 id 要稳定。** kebab-case，一次定好，中途绝不改名。规格、计划、下游操作都按这些 id 选工作，而不是去猜哪份规格是当前的。
- **依赖方向单向，不许成环。** 箭头只朝一个方向。两个模块互相需要，那它们就是一个模块。
- **接口待在边界上。** 地图只记录「billing 依赖 identity」；两者之间的契约写在提供方模块的规格里（怎么设计接口见 `api-and-interface-design`）。

**地图和每个阶段一样要过门禁。** 模块边界、依赖方向、建设顺序都得人工确认了，才开始写任何一个模块的规格。地图画错的代价很大，而评审十行表格的代价很小。

**然后按模块递归。** 按依赖顺序，对每个模块跑一遍「规格 → 计划 → 任务 → 实现」。每个模块有自己的规格，范围限定在该模块的目标、边界和成功标准内。评审通过的地图存到项目根，各模块的规格放在旁边，按模块 id 命名（`SPEC-identity.md`、`SPEC-billing.md`）—— 索引是这份地图，不是靠文件名去猜。

### Phase 1：规格

从高层愿景开始。不断向人提问，直到要求变得具体。

**先把假设摆到明面上。** 写规格正文之前，先列出你在假设什么：

```
我正在假设：
1. 这是 Web 应用（不是原生移动端）
2. 鉴权用基于会话的 cookie（不是 JWT）
3. 数据库是 PostgreSQL（依据现有的 Prisma schema）
4. 只针对现代浏览器（不管 IE11）
→ 现在纠正我，否则我就按这些往下写。
```

不要默默补齐含糊的需求。规格的全部意义就是让误解在写代码**之前**暴露出来 —— 而假设是最危险的一种误解。

**规格文档要覆盖六个核心部分：**

1. **目标** —— 我们在做什么、为什么做？用户是谁？成功长什么样？

2. **命令** —— 带参数的完整可执行命令，不是只写工具名。
   ```
   构建：npm run build
   测试：npm test -- --coverage
   Lint：npm run lint -- --fix
   本地：npm run dev
   ```

3. **项目结构** —— 源码放哪、测试放哪、文档放哪。
   ```
   src/           → 应用源码
   src/components → React 组件
   src/lib        → 共享工具
   tests/         → 单元与集成测试
   e2e/           → 端到端测试
   docs/          → 文档
   ```

4. **代码风格** —— 一段真实的代码片段胜过三段描述。包含命名约定、格式规则，以及「好输出」的例子。

5. **测试策略** —— 用什么框架、测试放在哪、覆盖率期望、哪类问题用哪层的测试。

6. **边界** —— 三档：
   - **总是做：** 提交前跑测试、遵守命名约定、校验输入
   - **先问再动：** 改数据库 schema、加依赖、改 CI 配置
   - **绝不做：** 提交密钥、改 vendor 目录、未经同意删掉失败的测试

**规格模板：**

```markdown
# 规格：[项目/功能名] — V[N]

## 目标
[我们在做什么、为什么。用户故事或验收标准。]

## 技术栈
[框架、语言、关键依赖及版本]

## 命令
[构建、测试、lint、本地起服务 —— 完整命令]

## 项目结构
[目录布局与说明]

## 代码风格
[示例片段 + 关键约定]

## 测试策略
[框架、测试位置、覆盖率要求、测试层级]

## 边界
- 总是：[...]
- 先问再动：[...]
- 绝不：[...]

## 成功标准
[怎么算做完 —— 具体、可测的条件]

## 不做（延后）
[明确排除在本版本之外的想法 —— V2 待办。每条一行：做什么，为什么延后。]

## 待定问题
[所有还没解决、需要人来定的问题]
```

**外部规格工具：** 这套流程不绑定格式。如果项目已经在用 OpenSpec 之类的规格系统，就沿用它那套产物格式和存放约定，别再另造一份 `SPEC.md`。本技能负责澄清、内容和确认门禁；已通过的规格长什么样、存在哪，由那个工具决定。

**把模糊要求翻译成成功标准。** 收到含糊需求时，转成具体条件：

```
需求：「让 dashboard 快一点」

重写后的成功标准：
- 4G 网络下 dashboard 的 LCP < 2.5s
- 首屏数据加载在 500ms 内完成
- 加载过程中没有布局抖动（CLS < 0.1）
→ 这几个目标对吗？
```

这样你才能朝一个明确目标去试、去重试、去解题，而不是猜「快一点」是什么意思。

**写完规格就停（关键）。** 规格保存之后：

1. 概述它，列出所有待定问题。
2. 请人确认，或者提出修改。
3. **立刻结束这一回合。** 不要在这回合里进 Phase 2、不要调 `planning-and-task-breakdown`、不要写代码。规划只能在下一个人工确认规格的回合之后开始。

### Phase 2：计划

拿着已确认的规格，产出技术实现计划：

1. 找出主要组件及其依赖
2. 确定实现顺序（什么必须先建）
3. 记录风险与应对策略
4. 分清哪些能并行做、哪些必须串行
5. 定义各阶段之间的验证检查点

> 这些步骤背后的依赖图与纵向切分机制以 `planning-and-task-breakdown` 为准。上面的条目只是轻量摘要；两者若有出入，以后者为准。
>
> **产出约定：** 计划存到 `tasks/plan.md`，任务清单记到 `planning-and-task-breakdown` 定义的位置（默认 `tasks/todo.md`；项目也可以指定外部跟踪工具）。`tasks/` 不存在就建。下游流程默认按这套约定找文件。

计划要可评审：人能读完说「对，就是这个路子」或者「不行，改 X」。

### Phase 3：任务

把计划切成可独立实现的任务：

- 每个任务能在一个专注的会话里做完
- 每个任务有明确的验收标准
- 每个任务带验证步骤（测试、构建、人工确认）
- 任务按依赖排序，而不是按「感觉重要」
- 单个任务不要改超过约 5 个文件

> 完整的任务粒度与依赖排序机制以 `planning-and-task-breakdown` 为准。下面的模板是轻量内联版；两者若有出入，以后者为准。

**任务模板：**
```markdown
- [ ] 任务：[描述]
  - 验收：[做完时必须为真的条件]
  - 验证：[怎么确认 —— 测试命令、构建、人工检查]
  - 文件：[会碰哪些文件]
```

### Phase 4：实现

一次做一个任务，按 `incremental-implementation` 与 `test-driven-development` 走。每一步只把规格里相关的那几节和必要的源文件读进来（`read_file` 指定行范围、`search_code` 定位），别一次性把整份规格灌进上下文。

## 让规格活着

规格是活文档，不是一次性产物：

- **决定变了就更新** —— 发现数据模型要改，先改规格，再实现。
- **范围变了就更新** —— 加了或砍了功能，都要反映到规格里。
- **把规格提交进仓库** —— 它属于版本控制，和代码放一起。
- **在 PR 里引用规格** —— 每个 PR 链回它实现的那一节。

## 规格演进：V1 收敛与后续改动

一份规格描述的是一个版本的工作。新想法和上线后的改动不去扩写它，而是排在它后面。

### 每个版本显式标号

在标题里标出这份规格描述的是哪个版本（`# 规格：发票流水线 — V1`）。已上线的增量折回原规格时，版本号往上抬 —— 标签始终说明这份规格描述的是系统的哪个版本，也让「那是 V2 的事」变成一个客观判断，而不是建到一半拍脑袋。

写规格阶段，进不了本版本的想法一律进 **不做（延后）** —— 记下来，别丢。这让 V1 的边界可执行：实现期间，不在规格「要求」里的东西都不做，哪怕它就写在同一个文件的延后区里。做到一半冒出新想法，塞进延后清单继续干活；重新定范围发生在版本之间，不发生在版本之内。

### 后续改动写增量规格

一份规格上线之后，新需求 —— 换存储引擎、把手动步骤换成 OCR、把延后的 V2 条目提上来 —— 另起一份小规格，而不是直接手改已上线那份。增量规格只写变化的部分：

```markdown
# 规格增量：[改动名]

状态：提案中

## 目标
[改动是什么、为什么。它落地了哪个延后条目或新需求。]

## 现状
[今天是什么样 —— 链回原规格里相关的章节。]

## 变更后
[改完之后什么为真。]

## 成功标准
[具体可测的条件 —— 包括哪些东西必须保持不变。]

## 边界
[只写相对原规格边界的增量；其余继承原规格。]
```

和原规格存一起（比如 `SPEC-postgres-migration.md` 放在 `SPEC.md` 旁边），走同一套带门禁的流程：人工确认 → 计划 → 任务 → 实现。一份增量规格只装一个改动，这样每个计划 / 实现周期都小而可评审。

改动上线之后，把结果折回原规格（见「让规格活着」），让它继续作为「系统现在是什么样」的事实源；同时把增量规格的 `状态：` 改成 `已实现`。原规格永远描述当前系统，增量规格描述的是迁移过程。

## 常见自我合理化

| 合理化 | 现实 |
|---|---|
| 「这个简单，不用写规格」 | 简单任务不需要**长**规格，但仍然需要验收标准。两行的规格就够。 |
| 「写完代码再补规格」 | 那是文档，不是规格。规格的价值在于逼你在写代码**之前**想清楚。 |
| 「写规格会拖慢我们」 | 15 分钟的规格省掉几小时的返工。15 分钟的瀑布胜过 15 小时的调试。 |
| 「反正需求会变」 | 所以规格是活文档。过期的规格也比没有强。 |
| 「用户自己知道要什么」 | 再清楚的请求也有隐含假设。规格就是把假设摆出来。 |
| 「这想法不错，直接并进当前规格」 | 建到一半扩范围，正是 V1 拖延的原因。放进「不做（延后）」，记下来但不扩大当前周期。 |
| 「功能已经有规格了，改动直接改它」 | 已上线的规格描述的是现状。增量规格让改动本身可评审；原规格是改动上线**之后**才更新，不是之前。 |
| 「这就是一个大功能，拆开是额外开销」 | 如果验收标准能聚成可独立验证的几组，单体规格会逼着下游每个任务都对着整份契约推理。十行能力地图是便宜的替代方案。 |
| 「拆解留到规划阶段做」 | 规划是在一份规格**内部**切任务。到那时过大的产物已经存在了 —— 模块边界和依赖方向必须在写规格之前定，不是之后。 |

## 红旗

- 没有任何书面要求就开始写代码
- 还没搞清楚「什么算做完」就先问「我可以开始写了吗」
- 实现任何规格和任务清单里都没提的功能
- 做了架构决定却不写下来
- 因为「要建什么很明显」而跳过规格
- V1 的要求在实现中途一路膨胀，新想法直接写进规格
- 改动已上线的功能却没有针对这次改动的规格，理由是「这功能已经有规格了」
- 写完规格，同一回合就开始做计划或写代码
- 一份规格的要求横跨好几个可独立验证的能力
- 模块边界或建设顺序是在实现过程中被隐式定下的，因为前面没批准过能力地图

## 验证

进入实现之前，逐条确认：

- [ ] 规格覆盖六个核心部分（增量规格只覆盖受影响的部分 —— 至少目标、成功标准、边界增量 —— 其余继承原规格）
- [ ] 人已经评审并确认了规格
- [ ] 保存规格之后就结束了回合；确认发生在下一个回合
- [ ] 成功标准具体且可测
- [ ] 边界三档（总是 / 先问再动 / 绝不）已写明
- [ ] 规格已存成仓库里的文件
- [ ] 从本版本砍掉的想法记录在「不做（延后）」里，既没被悄悄丢掉，也没被悄悄塞回来
- [ ] 如果这是对已上线规格的改动，那它是一份引用原规格的增量规格，不是把原规格重写一遍
- [ ] 如果请求捆了多个可独立验证的能力，能力地图（模块 id、依赖方向、建设顺序）已先于任何模块规格被批准
- [ ] 每一份模块规格都能对上已批准地图里的某个模块 id
